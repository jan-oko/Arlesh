# Filtering Logic

*One area of the [Arlesh design specification](../../SPEC.md).*

Filters apply to task/goal lists. Any number of filters can be active simultaneously, each in one of three modes:

- **Any** — item must match at least one Any-mode filter
- **All** — item must match every All-mode filter
- **Exclusion** (shown as **Not**) — item must not match any Exclusion-mode filter

Combined logic: `(union of Any-filters) AND (intersection of All-filters) AND NOT (union of Exclusion-filters)`

Filterable fields: status (the presets, and Task/Goal/Project status), tag, **Under** (any ancestor — parent domain/task, Project, Aspect, Goal; called *Antecedent* until 2026-09-26), **Depends on** (called *Dependency*), verdict, scope state (including planned/unplanned), blocked, agentic, asynchronous, delegated (its own [tri-state pill](#delegated-pill)).

<a id="adding-modes"></a>**Adding a filter, and its mode** (2026-09-26). Every place that adds a value — a pill in the [Filter menu](mindmap-view.md#filter-menu), an option in one of its search dropdowns, a result in the `Ctrl+F` [filter search](mindmap-view.md#filter-search) — reads the mode off the keys held: **click / Enter adds as All**, **Shift+click / Shift+Enter as Any**, **Alt+click / Alt+Enter as Not** (Alt wins over Shift). Values used to be added as Any; All became the default because a single value reads the same either way and All is the one that narrows further as you add. An added value's chip, and its set pill in the Filter menu, cycle **All → Any → Not → All** on click, and Delete or Backspace on either removes it. (A tag clicked on a List View row, and a path-header segment `Ctrl`/`Alt`-clicked, keep adding as they did: Any, and include/exclude.)

**Yes/no dimensions** — Blocked, Agentic, Asynchronous, and **Private** while Private Mode is on — are **one pill each**, not a pair of values, and take the three modes like any other value: adding the pill means "is blocked" (All), with Shift "is blocked, or one of the other Any flags" (Any), with Alt "is not blocked" (Not), and a click on the added pill cycles **All → Any → Not** like every chip. The flags form **one pill group** for the formula above — Any among them is an Any *across* them — so Agentic (Any) with Asynchronous (Any) keeps what is agentic **or** asynchronous, while All and Not still read per flag. (Until 2026-09-27 a flag had no Any and just flipped; the user ruled that flags must allow it.) A flag is stored as a single "is X" value in its mode; a tab stored with the old "not X" value reads as the Not of "is X" (and its Not as All) on load. Its chip reads **Blocked** or **Not blocked**. A Commitment or a wait answers only the Private flag: the others ask about Tasks.

**Where the modes are written down.** Neither the Filter menu nor the `Ctrl+F` search carries a hint line; the adding modes, the cycle and removal are listed in the keyboard cheat-sheet (`Ctrl+Shift+/`) in a **Filters** tab after Global.

**Private** (2026-09-27) is a yes/no pill of the List View's, offered only while **Private Mode** is on — with it off every private node is hidden already. A row is private when its node is marked Private or sits under a node that is, the same reading Private Mode hides by, and the pill applies to Task, Commitment and Expectation rows alike. **Turning Private Mode off removes the Private / Not private pill**, with a toast saying so (Reset, which turns it off, removes it too). It is List View only, as the other yes/no pills are: the Mindmap does not read the pills. They are defined in `src-tauri/src/filters/pills.rs` too, where an [MCP](mcp-server.md) read reaches them, and the conformance corpus holds the two evaluators together.

The presets judge each kind by its own rule: a Task and a Goal by their status and effective Archival, a Commitment by its Verdict, and an **Expectation** by its status and Archival — its stored archive, or derived once it is released and its window has passed (see [*Expectations*](resources.md)). A node beneath a Task or Commitment **archived by hand** reads as archived through inheritance, worked out in the board load before either evaluator runs (Task 269). A **delegated Task** is not archived (ruled by the user, 2026-10-03): it answers to the **Delegated** pill below, and a dependency on a pending Expectation makes a Task **blocked**; a dependency on a done Asynchronous Task is met, whatever the wait it spawned is doing. A spawned wait — derived while an Asynchronous Task with a template is done — is judged by the same Expectation rules as a stored one, reading its status and archive from its overlay (pending and live when it has none) and its Check every from the template. "Asynchronous" is the Task's own flag. A **Compound** Task is judged by its **derived** status exactly as another Task is by its stored one, and is **blocked** when its derived block reason says so (every open sub-item blocked): both are worked out in the board load, before either evaluator reads the board, so Rust and TypeScript read the same status and the same block (see [*Compound*](resources.md#compound)). The List View's **Expectations** option, like Unblock, is a flag beside the preset (`BoardFilter::expectations`) rather than a preset of its own, and the Mindmap ignores it.

<a id="delegated-pill"></a>**The Delegated pill** (Task 269, ruled by the user 2026-10-03). Delegation used to count as archival — a delegated Task was hidden wherever an archived one was, and the Archived pill governed it. It has a tri-state pill of its own now, beside Archived and Backlog in every view's Filter menu (key `g`, and a switch in `Ctrl+F`), kept with the tab (`BoardFilter::delegated` / `delegatedMode`; a tab saved before it reads as off):
- **Off** (as the preset says) hides a delegated Task wherever archived ones were hidden, except Do, as before: Plan and Start drop its own match; All, Do and Backlog leave it. Its delegation wait answers the Expectation rules beside it.
- **Include** shows it under Plan and Start, judged by the preset's other rules like any Task.
- **Exclude** hides it with its subtree under every preset, All and Do included. In the flat list it hides the row itself, as the Archived pill does.

The node searches follow the pill: they leave delegated Tasks out unless it is on Include (see [*Archived nodes in search*](mindmap-view.md#search-archived)). The Zen View drops every delegated Task whatever the pill says (see [*Zen View*](zen-view.md#the-grid)). The corpus pins it with the `delegation` board (`conformance/preset-filters.json`).

**Not built yet:** delegate-to, Person/Event/Thread/Scope links, and filtering by a specific planned scope. They stay specced; nothing filters on them today.

When delegate-to is built, a delegate is a Person (the Agent delegate was removed on 2026-10-01). Neither reads the Agentic flag, which is its own field.

<a id="agentic-statuses"></a>**A Task's status is read in its own model** (Task 68f, 2026-10-01; see [*Agentic statuses*](resources.md#agentic-statuses)). The presets dispatch on the model first — the fact `agentic` beside a Task's `status` (`NodeFacts::agentic`; `taskStatus.kind` on the frontend) — and only then on the value; a value is never read across models by its spelling (an ordinary row spelled `review` is not Review). An ordinary Task answers exactly as before. An **Agentic** Task: **Plan** shows every one not Done; **Start** shows To Do, **Review** always, **Doing** while it has a To Do child (as In Progress), and **On Agent** only while the **On Agent** pill is on (`BoardFilter::show_on_agent` / `showOnAgent`, off by default, kept with the tab and carried to an MCP read like the rest of the filter); **Do** shows Doing and Review, and On Agent only with the pill on; the three "shows Started tasks" settings never touch Review or On Agent. All and Backlog read it as any Task. The Zen View reads under Do, so the same pill shows On Agent there. Review is derived by the backend before either evaluator runs, so both read the same value. The conformance corpus carries an `agentic` board with a case for each (`conformance/preset-filters.json`), and the capacity-lock board's Agentic Tasks hold Agentic statuses.

**Where the definition lives.** The status presets and the override pills are defined once, in `src-tauri/src/filters/`, so that the [MCP server](mcp-server.md) and the two views answer the same question the same way — an agent reading the board and a person looking at it disagreeing about what is live, silently, is the failure this exists to prevent. The frontend does **not** call into that definition: its filter pass is synchronous and runs per render, and an IPC round trip in front of every selection move would be a regression, so it keeps a synchronous evaluator of its own. The two are held together by `conformance/preset-filters.json` — a corpus of boards, filters and kept nodes, written from this specification and generated by neither implementation, which the Rust tests and the frontend tests both replay. Changing a rule in one language and not the other fails the other language's build. The List View's own pills and kind selector are in it too (Task 122, phase 4): `filter.kinds` and `filter.pills` in the corpus, `crate::filters::pills` in Rust and `list-filter.ts` in the frontend. Two more corpora pin the List View's and the Zen View's per-render rules the same way: `conformance/list-sections.json` — which rows the Review, Overdue and Asynchronous sections lift, and when each is drawn (`crate::filters::sections`, `list-sections.ts`) — and `conformance/zen-contents.json` — the Zen View's grid and strips, and which views read under a preset of their own (`crate::filters::zen` and `views`, `zen-contents.ts` and `view-preset.ts`). The **focus exemption** below is deliberately not part of it: it is a render-time overlay on the view's own selection, not a filter rule.

**A Plan's position is a derived fact, like Timing.** The backend derives where each Task's own Plan stands at now — before, within or after its window, on the 02:00 day boundary — beside the Time Scope's Timing in the same lifecycle derivation, and both evaluators read that value rather than resolving dates themselves. **Start** is the one preset that reads it: it drops a Task whose Plan is still ahead, keeps one whose Plan ended unfulfilled, and — as an interim rule pending Plan inheritance (`Arlesh-67y`) — reads an unplanned Task by its nearest planned ancestor Task's Plan. The walk carries that inherited value down the way it carries a container's status; the List View, with no walk, asks each row's ancestor chain. See the Start preset in [*Mindmap*](mindmap-view.md) for the full rule.

**Start drops both ends of a window.** Timing is the other derived fact Start reads, and it drops an item on **either** side of its window: **Lapsed** (passed) and **Pending** (not begun — ruled by the user, 2026-09-27). **An Overdue item is the exception** (ruled by the user, 2026-09-30): Start reads the derived **Overdue** flag beside Timing and keeps an item it is set on although its window has passed — `is_startable_window` / `isStartableWindow`, the one predicate both evaluators apply to Tasks, Goals and waits. The flag is never set on a finished or effectively Archived (Missed) item, so nothing Start dropped for being settled comes back; blocked, backlogged, delegated (with the Delegated pill off) and planned-ahead items drop by their own rules, Overdue or not. Timing is already the effective window's, so the filter inherits nothing itself: a Task or Goal with no window of its own arrives Pending when its nearest scoped ancestor's window is still ahead, and a wait with none arrives Pending while what it hangs under is. A Pending Task or Goal fails its own match only; a Pending wait gates its subtree, so its check tasks go with it. Both evaluators apply the same predicates (`is_unopened_wait` / `isUnopenedWait` for the gate), and the List View asks a row's ancestor chain for the gate as it does for a shelved Project.

**A block from a child dependency does not hide that dependency** (ruled by the user, 2026-10-01). Under **Start** a blocked Task or Goal gates its subtree — except the descendants it **depends on** and has not had met, which are the work that unblocks it. Such a child dependency shows if it passes Start on its own merits, **its own subtree with it**, and the blocked node stays on screen only as its ancestor: it still fails its own match. Everything else under the blocked node stays hidden — its other children, and every child of one blocked by an **explicit reason**, by a **capacity lock**, by a **Compound** Task's derived block (its open sub-items all blocked — a reason, not a dependency edge), or by a dependency on something **outside** its subtree. A node with several blocks still lets its child dependencies through and hides the rest. Where one blocked node sits under another, a descendant comes through only if **both** depend on it, and a child dependency that is itself blocked gates its own subtree in turn. The backend sends each Task's unmet dependencies as node ids (`blocking_dependencies` / `blockingDependencyIds`); the walk carries the gate down (`gate_below` / `gateBelow`, `is_held_by_block` / `isHeldByBlock`), and the List View folds it down each row's ancestor chain (`heldByBlockedAncestor`). So a subtask under a parent blocked by a written reason stays hidden even when the reason names that subtask's work; making it a dependency of the parent on the subtask is what lets it through.

**The agent capacity lock is a block, not a filter rule** (ruled by the user, 2026-10-01). While agents are at capacity, every Agentic Task not yet Done is **derived blocked** (see [*MCP Server*](mcp-server.md), *Agent capacity*), and the presets read it as they read any block — Start drops it with its subtree, Unblock lists it — on the app and in the MCP snapshot alike. There is no rule for it in either evaluator: the backend derives the reasons onto the load's `block_reasons` (marked `derived: "agent_capacity"`) before either reads it, so both see an ordinary `is_blocked` fact. The corpus holds that with the `agent-capacity` board: the facts are what the derivation produces, and the cases show Start and Unblock reading them. (A first cut, 2026-09-30, made it an app-only Start rule that the MCP ignored; it never shipped.)

**Focus exemption.** The **selected** node renders whatever the filter says about it, for as long as it stays selected — so a node that stops matching *because of your own edit* (completing a Task under Plan, cycling a Task to a Goal under Do, marking something Private) stays where it is instead of vanishing out from under you. It renders **dimmed**, carrying the status-icon badges that already say why it no longer matches; there is no new chrome. It overrides **every** hiding rule, the hard-hiding ones included — Private Mode, the Info/Flow type toggles, a shelved Project, a blocked subtree under Start — not just the soft preset/tag/pill filters. That is safe because toggling any of those *is* a filter change, which ends the exemption, so a private node can never survive into a Private-Mode-off view; the only case that survives is one you just marked private yourself, while still on it.

It **ends** when focus leaves — the selection moves, or Escape clears it — and on filter change, subtree change and reload. Nothing about it is persisted. It never resurrects a node: arrowing away removes it, and arrowing back does not bring it back, because it is no longer on screen to arrive at.

The exemption covers the focused node **and every ancestor needed to reach it**, and nothing else. The Mindmap keeps a non-matching node only as the ancestor of a match, so exempting a node without its chain would draw it detached; an ancestor that surfaces only to carry it is dimmed too, and carries nothing else with it — revealing (say) a private Project as an ancestor does not spill the rest of its subtree into the view. The List View needs no chain: its rows are Tasks, and a row's hidden ancestors are already named in its path header, so there the exemption is exactly one row, held in its own place in the list.

It is a **render-time** exemption: the filter's definition is unchanged and the filter's own answers are unchanged. Anything that counts, filters or exports off the filter sees exactly what it saw before — only the view holds the extra node.
