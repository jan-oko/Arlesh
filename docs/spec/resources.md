# Resources

*One area of the [Arlesh design specification](../../SPEC.md).*

## Domains

Domains are organizational containers for Tasks and Goals. A Domain has a title, description, and a nullable parent Domain.

There are four domain subtypes:

**Aspects** — six built-in, color-coded top-level domains. Not user-managed. Fixed roots of the domain tree.

| Name        | Color      | Focus                                                                 |
|-------------|------------|-----------------------------------------------------------------------|
| Body        | Red        | Physical needs: health, physical pursuits                             |
| Connections | Purple     | Psychological needs: social activities                                |
| Growth      | Green      | Fulfillment needs: hobbies, knowledge, creative/technical construction|
| Duty        | Blue       | Moral duty: activities for others, social activism                    |
| Flow        | Gray       | Flow-state needs: finance, cleaning, bureaucracy                      |
| Self        | Light gray | Self-determination: introspection, goal-making, task management       |

**Projects** — large domains (hobby, habit, workplace, etc.). Parent must be an Aspect or another Project. May be linked to a knowledge-base directory. Status: **Active / Achieved / Frozen / Archived**. May carry a **beads id** (see *Beads id* below).

**Domains** — general-purpose organizational containers. Can parent Goals, Tasks, Tags, or other Domains.

**Tags** — flat leaf nodes used as resource markers. Each Tag has a title and a parent (`parent_id`, a row in `domains`). Tags cannot parent other Tags, and hold no structural children — with one exception: a Tag may hold **Info notes**, which is what a label carries when it needs explaining (`Shift+I`, or dropping a note onto it). `Tab` on a Tag is refused, because the child it creates is a Task. Tags appear in filtering as a first-class primitive.

## Knowledge Base

The knowledge base is externally managed (Obsidian). Arlesh manages specific note types as structured entities.

**People** — represent persons. Fields: name (= note title), aliases (list of strings), linked note. (Discovery from the vault is not built yet — see *Not built yet*.)

**Scopes** — time range entities. Not manually created, and never stored: a scope is derived from its kind and start date (or, for an Exact window, its two datetimes), and referenced everywhere by its value key (e.g. `{"kind":"week","date":"2026-09-20"}`; see [*Scopes are derived*](time-scopes.md)). Canonical kinds:

| Kind        | Definition                                      |
|-------------|-------------------------------------------------|
| Season      | Three-month period (Autumn: Sep–Nov, Winter: Dec–Feb, Spring: Mar–May, Summer: Jun–Aug) |
| Month       | Calendar month                                  |
| Week        | Sunday–Saturday, custom numbering from the week holding 1 January (week 1) — so a year runs to week 53, or 54 when a leap year starts on a Saturday (not ISO 8601); never split at New Year — see [*The week across New Year*](time-scopes.md) |
| Day         | Single date; corresponds to an Obsidian note at `{yyyy}/{mm MMMM}/{yyyy-mm-dd}.md` |
| Part of Day | Sub-day band: Morning (06–12), Noon (12–15), Afternoon (15–18), Evening (18–22), Night (22–02), Premorning (02–06). Start inclusive, end exclusive. |

Beyond the canonical hierarchy, an **Exact** scope is defined by two arbitrary datetimes at minute precision (e.g. for a one-off deadline).

Canonical scope containment is hierarchical, on two ladders: Part of Day ⊂ Day ⊂ Week, and Day ⊂ Month ⊂ Season. A Week is not inside a Month — a Sunday–Saturday week can straddle two months, and two seasons — so a Day has a Week, a Month and a Season, a Month a Season, and a Week none — each derived from the Day's date, never stored. **Night (22:00–02:00) crosses midnight and is parented to the Day it starts on** — and is wholly inside it, because Day, Week, Month and Season all run 02:00 → 02:00 (see [*The day boundary*](time-scopes.md)). Every scope resolves to concrete datetime boundaries (a pure backend function does the resolution, with no cache — it is cheaper than a lookup); Parts of Day and Exact scopes carry a time-of-day component.

A scope is **active** when it contains the current datetime.

**Containment-based filtering** is evaluated as interval containment on resolved datetime boundaries: filtering by a scope returns every item whose own scope window is wholly contained within it. This works uniformly for canonical, multi-week, and exact scopes.

**Events** — represent events. Fields: datetime or scope, title, optional linked note.

**Threads** — concretized trains of thought. Fields: title, linked note. (Discovery from the vault is not built yet — see *Not built yet*.)

## Goals

Goals represent desired states. Fields: title, parent (Project / Goal / Domain), tags (list), KB resource links (People, Events, Threads, Scopes), status, blockers, beads id.

**Status:** Active / Achieved / Frozen / Archived

Goals are never List View *rows*; they appear instead as a segment of a row's **path header** there (see [*List View*](list-view.md)). (Commitments and Expectations are drawn in their own bands above them, or as rows among them, by a setting; see [*List View*](list-view.md).) Goals can be depended on by Tasks; a Goal-dependency blocks a Task until the Goal is Achieved.

## Tasks

Tasks represent action items. Fields: title, parent (Project / Goal / Domain / Task / Commitment), tags (list), KB resource links, status, blockers, dependencies, delegation, agentic, compound, beads id.

**Status:** To Do / In Progress / Started / Done

**Started** (Task 9e3, grilled with the user 2026-09-30) — begun and left in a middle state, but not being done right now: paused work. It is a fourth **stored** status (`started`, migration 0084 widening the CHECK on `tasks.status` and `task_overlays.status`), not a derived one; nothing sets it on its own.

- **Kinds.** Tasks and **Habit occurrences** only, as In Progress is — a wait's check task too, since it is a Task row. Not Goals, Commitments or waits. An occurrence keeps Started in its overlay's own `status` column, exactly as it keeps In Progress; nothing else about the overlay changes.
- **Keys.** `Alt+Enter` sets **To Do** or **Done** to Started, and flips **In Progress ↔ Started** (pause / resume) — in the Mindmap, the List View, the Steps View and the Zen View. `Enter`'s cycle is unchanged (To Do → In Progress → Done → To Do); `Enter` on a Started Task goes to In Progress. The Filter menu's own `Alt+Enter` (add a filter as Not) stays: the menu holds the keys while it is open. The Task editor offers Started as a fourth status pill.
- **Blocked.** `Alt+Enter` is refused while the Task is blocked, as `Enter` is, in every view. A Task that becomes blocked after being Started **stays Started**.
- **Beginning work.** In Progress and Started together are *begun* work (`TaskStatus::is_begun`). **Starting** a Task is the move into either from To Do or Done: that is what the Spec rule below guards — an Agentic Task with no Spec cannot be set Started any more than In Progress — and what takes a Task out of the **Backlog**, with the same toast (worded for Started). Moving between the two — pausing and resuming — is not a start, so it never asks for a Spec again.
- **Everything else reads Started as unfinished work, like In Progress.** It does not resolve a Time Scope (Timing and Resolution treat it as not done), it still blocks a Task that depends on it, it counts as open for a Habit occurrence's completion guard, and it is not a direct To Do child — so it does not keep an In Progress parent under Start.
- **Icon.** In Progress's glyph with the inner circle **unfilled**.
- **Presets.** Plan shows Started Tasks. **Start** shows them by default; **Do** and the **Zen View** hide them by default. Three separate app-wide settings switch them: *Start shows Started tasks* (on) and *Do shows Started tasks* (off) under Settings → General, and *Show Started tasks on the grid* (off) under Settings → Zen. They are stored with the other display settings (`startShowsStarted`, `doShowsStarted`, `zenShowsStarted` in the persisted `arlesh-display` store), filled into the board filter by the views rather than kept with the tab, and carried to the backend as `BoardFilter::start_shows_started` / `do_shows_started` so an MCP read asks the same question. The Zen View reads under Do with its own setting in Do's place.
- **MCP.** `arlesh_tasks.set_status` accepts `started`, as a compare-and-set like the other statuses.

<a id="compound"></a>**Compound** (Task f99, grilled with the user 2026-09-30). A Task can be set to **consist of its sub-items**: its status is then **derived** from its subtree and never set by hand. A stored boolean (`tasks.compound`, NOT NULL, default false, migration 0086) that **does not inherit** — a Task beneath a compound one keeps its own status unless it is marked itself.

- **What counts:** the **whole subtree** — Tasks (Habit occurrences and a wait's check tasks included), Goals, waits (Expectations, stored and derived) and Commitments. **Infos never count.** Backlogged and delegated items still count. Only what is **effectively Archived** is left out, with everything beneath it — *except* an item archived **by finishing** (a Done Task whose window has passed, an Achieved Goal, a settled Commitment), which still reads as Done and counts as Done. Ruled while building: left out, a compound Task whose steps were all finished inside its window would fall back to To Do the moment the window closed and then lapse unfinished.
- **How each item reads:** a Task, its status; a Goal, **Done** when Achieved and To Do otherwise; a **pending wait** or an **Unresolved Commitment**, **Started**; a released wait or a Commitment with a verdict (Kept or Broken), **Done**. There is no count display ("3/5") for now.
- **The progress rule:** **Done** when every counted item is Done. Otherwise **In Progress** if any item is In Progress. Otherwise **Started** if any item is Started or Done. Otherwise **To Do** — and To Do when nothing is counted.
- **Nesting:** a compound Task inside a compound Task is counted by its **derived** status, and its subtree counts for the outer one too (the rule reads the whole subtree). The inner one is resolved first, and its own lifecycle re-derived from its derived status before the outer one reads it.
- **Where it is computed** (settled while building): on the **backend, on every board load** (`tasks::compound`, run inside `mindmap::load` before anything reads the board). It is **never stored**: a descendant changing, a Habit deriving a new occurrence or a window passing all change it without a write, and a stored copy would go stale on exactly those. Because it happens in the load, every reader sees the derived status as the Task's `status` — the views, the presets and filters on both sides (Rust's `filters` and the TypeScript evaluators read the loaded status, so they agree by construction; `conformance/preset-filters.json` writes a compound Task into a board with the status it is served with), the MCP snapshot and `arlesh_tasks.get`, the dependency rule (a Task depending on a compound Task waits for its **derived** Done) and the Task's own lifecycle: a compound Task whose derived status is Done resolves its window as Completed. It stays fresh the way everything on the board does: every write ends in a reload, and a board-changed broadcast reloads the other windows. The stored `status` column keeps whatever it last held and is ignored while the flag is on.
- **Manual status writes are refused**, with a toast saying to change the sub-items or turn compound off: `Enter` and `Alt+Enter` in the Mindmap, the List View, the Steps View and the Zen View, a click on the status glyph, and MCP `set_status` (the backend refuses any request naming a status, `TaskError::CompoundStatus`, so nothing gets past it). `X` is a Commitment key and never acts on a Task, so it has nothing to refuse. In the Task editor the status pills show the derived status, **disabled**, with a line saying the status comes from the sub-items; the save sends no status.
- <a id="compound-block"></a>**Derived block** (asked for by the user in review, 2026-10-01: "if all open items are blocked, so is the compound"). A compound Task is **blocked when every one of its open counted items is blocked**. *Open* is a counted item that is not Done by the progress rule (an Achieved Goal, a released wait and a resolved Commitment are Done, so never open). *Blocked* is the board's ordinary rule — a block reason of any kind, or a dependency on a Task not Done, a Goal not Achieved or a pending wait — and a compound Task inside counts by its own derived block too, worked out innermost first. With **no open item** (everything Done, or nothing counted) it is not blocked. A **pending wait or an Unresolved Commitment is open but has no blocked state**, so one of them keeps the compound unblocked (built this way and flagged for the user). It is computed on the backend in the board load, after every status is final, and served as a **derived block reason** (`BlockReason.derived = compound`, reading "All open sub-items are blocked", translated by the frontend) beside the stored ones — never stored, so it goes the moment a sub-item is unblocked or finished. Everything blocked already implies follows: the stop sign, Start dropping it with its subtree, Unblock showing it, a dependent waiting on it, the MCP snapshot and `get` listing the reason. In the Task editor it is a read-only row of its own under the block reasons, and an editor save never writes it back. `conformance/preset-filters.json` carries a compound board whose blocked compound is written as the blocked Task it is served as.
- **Blocked by its own reasons:** derivation of the *status* ignores blocking. A compound Task that is blocked **can read In Progress** (or Started, or Done) when its sub-items say so — the blocked refusal guards a *manual* start, and nothing here is a start. The same goes for the Spec rule (an Agentic compound Task with no Spec may read In Progress) and the Backlog rule (reading In Progress does not take it out of the Backlog). The glyph still shows the blocked mark while it is blocked.
- **Switching it:** a **Compound** switch in the Task editor, beside Asynchronous, and the bare **`V`** key on the selected Task in the **Mindmap, List View, Steps View and Zen View** (bare V was free; `Ctrl+V` is Paste and chords match exact modifiers). MCP `arlesh_tasks.update` takes `compound`. Duplicating a Task copies the flag.
- **Switching it off keeps the derived status** as the stored status, in the **same write** — one Gesture, one `Ctrl+Z`. A request that switches it off may name the status to keep (the editor's Save sends the status its pills show, which starts at the derived one); one that names none — `V`, the MCP — has the backend name the derived status for it. Keeping it is **not a start**: it asks for no Spec and does not clear the Backlog, since the Task already showed that status. Kept at Done, it records the completion (`done_at`), as any Done does.
- **Look:** the status icon is drawn from the derived status with its **outer ring dashed**, in every view that draws the icon (the Zen View draws no icon on an In Progress card, and so none there). No extra badge.
- **Stored Tasks only** (settled while building). A **Habit occurrence** or a check task cannot be made compound — `V` on one is refused with a toast, the editor offers no switch, and the backend refuses it (`TaskError::CompoundOnDerived`) — because its row lives in the Habit's overlay, which has no place for the flag, and its status is the Habit's record of that iteration. Occurrences **count** as items like any Task, and a stored compound Task hung on an occurrence works as anywhere else.
- **The waits a compound Task itself draws** (settled while building, forced rather than chosen): a delegated compound Task's **delegation wait** exists exactly while the Task is not done, so it follows from the Task's status rather than being part of it — the Task does **not** count it, or it could never be Done; an ancestor does. An **Asynchronous** compound Task **spawns no wait** while it is compound: nothing is done by hand, so nothing is done that starts one. Switching it off at Done records the completion, and the wait begins then.

**Blockers:** A Task (and a Goal) can carry an **ordered list of explicit block reasons**, edited in its editor (add / remove / reorder rows). A Task is **additionally** blocked *virtually* by any dependency on a non-Done Task, a non-Achieved Goal or a Pending Expectation, with reason `"Blocked by {kind} {id} ({title})"`. The two combine: a Task/Goal reads as **blocked** on the canvas (red stop-sign) when it has **any** reason — explicit or virtual. Explicit reasons live in their own `block_reasons` table (polymorphic `owner_type`/`owner_id`, ordered by `position`); virtual reasons are derived at read time from the dependency edges, never stored. Cross-table type conversion copies the explicit reasons to the new node.

**Dependencies:** Tasks can depend on other Tasks, Goals or **Expectations**. Circular dependencies are rejected at write time; an Expectation depends on nothing, so no cycle can run through one.

<a id="quick-dependency"></a>**The quick dependency picker (`D`)** (asked for by the user, 2026-09-29). Bare **`D`** on the Mindmap, the List View and the Steps View gives the selected Task a prerequisite **without opening the editor**, as `P` sets its Plan (see [*The quick Plan picker*](time-scopes.md#the-quick-plan-picker-p)). It opens a **small search bar** drawn at the selected node, row or card, and searches the way `Ctrl+O` does: nothing until you type, titles matched in any case, a title shared by several results told apart by its parent path, each result naming its kind. **↑ ↓** move the highlight, **Enter** or a click adds the highlighted one, **Esc** or a click outside closes and writes nothing; while it is open it holds the keyboard, so the view's own letters stay quiet. It is not bound in the Plan View.

- **What it offers:** **Tasks** and **Goals** (stored ones and Habit occurrences) and **stored Expectations** — everything a Task may depend on. The user first asked for Tasks and Expectations, and ruled on 2026-09-29 that Goals belong in the search too, under the same exclusions. A derived wait (a check task, a delegated Task's wait, a spawned wait) is not offered: an Expectation edge names a stored row.
- **What it leaves out:** the Task itself; what it already depends on (Task, Goal or Expectation); and every Task that already depends on it, directly or through a chain, since that edge would close a cycle the backend refuses. A Goal or an Expectation depends on nothing, so no cycle runs through one. The picker reads the board's effective edges (`list_all_task_dependencies`) when it opens to decide this, so an impossible pick is never offered. Archived nodes follow the node search's own switch (see [*Archived nodes in search*](mindmap-view.md#search-archived)).
- **What it acts on:** a Task with a row of its own — a stored Task or a Habit occurrence — which is what the dependency model lets depend on something. Anything else — a Goal, a Commitment, an Expectation, a wait's check task, a folded run of Habit history, a flow item (whose dependencies are the template's, set in the Flow editor), the Steps View's board card — is **refused by name** in a toast, as `P` refuses what holds no Plan. A Mindmap **multi-selection is refused** with a toast asking for one Task (ruled by the user, 2026-09-29): the picker adds one prerequisite to one Task, and acting on the lead alone while the rest stay selected would drop them silently.
- **The write** is the editor's own `add_task_dependency`, one **Gesture**, so one `Ctrl+Z` takes it back. A refusal the search could not foresee still comes back from the backend and is shown as a toast naming both nodes and the backend's reason, never dropped.

**Delegation:** A Task can be delegated to a **Person** or to the **Agent** — its **Delegate**. Delegation is a `(kind, id)` pair rather than a Person id (`tasks.delegate_kind` / `delegate_id`), so handing work to an agent does not mean inventing a Person called "Agent": a knowledge-base entity standing for something that is not a person. There is one Agent target, and it carries no id; naming individual agents is a later question. `delegate_id` still references `people`, since every id it can hold is a Person's, so a delegate naming no Person is refused and a Person who is someone's delegate cannot be deleted. A Delegate says who holds the work and dispatches nothing. On the wire it is `{"kind": "person", "id": N}` or `{"kind": "agent"}`, and `null` for none.

**A delegated Task has every effect of archival.** Someone else holds it, so it is hidden wherever an archived node is hidden: Plan and Start drop it (Start with the lapsed ones), the Archived pill's Include force-shows it and its Exclude hard-hides it, and it keeps its own status throughout. Do is no exception to the archival rule, which never touched Do — an in-progress delegated Task still shows there. What it is waiting on stays in view: while it is not done it carries a **virtual child Expectation** — "done by its delegate" — which answers the ordinary Expectation rules below. That wait is derived at read time and never stored; it has no Check every, and it is **released exactly when the Task is done**, which is simply the moment it stops being drawn. It cannot be released by hand (the release gesture refuses, saying so), and it has no editor of its own: `E` on it opens the Task's.

**Agentic:** A Task can be marked **Agentic** — work that suits being handed to an agent. It is a stored three-state flag (`agentic` — NULL / true / false), not a boolean, because it **inherits downward and is overridable**, the rule specced for Delegation: a Task with no value of its own reads its nearest flagged ancestor, so marking a whole branch is one edit, and an explicit value replaces what would have been inherited — including an explicit **not agentic**, which is how one Task comes back out of an agentic branch. The value inherits *through* Goals, Projects and Domains, which carry no flag of their own.

It is **Tasks only**: an agent performs actions, where a Goal is a desired state and a Commitment is kept rather than done. It is also **independent of Delegation** — the flag says the work suits an agent, a delegate says who holds it, so a Task may be both, either or neither, and a delegated/undelegated filter would be untouched by it. Set from the Task editor's **Agentic** control, in its **Advanced** section (Inherit / Agentic / Not agentic; `Arlesh-cz2` briefly moved it beside Asynchronous, and the user moved it back with its whole brief on 2026-09-24 — Asynchronous stays where it is), which opens by itself while the Task has an own flag, is delegated to the Agent or has a brief written, and from the bare **A** binding in the Mindmap and List View, which is a **two-state toggle over the resolved value**, not a cycle through the stored one: it reads what the Task currently *reads as* and writes the opposite — agentic → explicit *Not agentic*, anything else → explicit *Agentic*. The flag stores three states but a Task only ever shows two, and *Inherit* under a non-agentic parent is the same picture as an explicit *Not agentic*, so a cycle spent a press moving between them with nothing on screen to show for it — marking a fresh Task agentic appeared to take two presses. The consequence is deliberate: **the key can no longer return a Task to *Inherit***, which is an editor-only state, and a press on a Task that was merely inheriting *yes* pins it to an explicit *no*. That is the price of no press being invisible. Creating a sibling with `Shift+Enter` carries over the source Task's **own stored** value, explicit or not-set — the stored column, never the resolved one, since freezing an inherited *yes* into an explicit one would silently cut the new Task off from the ancestor deciding for it, which the ordinary downward rule already covers. It is shown as its own **status-row badge** in both views, on a Task that reads as agentic whether it said so itself or inherited it; and filterable as its own List View pill dimension. Duplicating a Task copies it, all three states alike. Beside the flag in the Task editor sits a one-click **Delegate to agent** button, offered on a Task that reads as agentic (its own flag, or an inherited one while it is on *Inherit*) and on any Task already delegated to the Agent, so an Agent delegate can always be taken back after the flag that earned it is gone. It toggles Delegation between the Agent and nobody — pressed on a Task delegated to a Person, it replaces the Person with the Agent — and is staged like every other field, so Cancel discards it. Nothing about it dispatches anything.

**The agentic brief** (`Arlesh-cz2`, settled with the user on 2026-09-24). Agentic is an **object**, the way Asynchronous is a flag with a template: while a Task reads as Agentic it carries a **brief** — what an agent reads about the work, in place of `bd show`. The **flag keeps inheriting** exactly as above; the **brief is the Task's own and never inherits**, so every agentic Task under an agentic branch has a brief of its own to fill. It holds a **Priority** (**MW**, **A**, **B** or **C**, the most urgent first, or none — four levels, the user's scale since 2026-09-25; stored as its rank 0–3), **Spec** (what to build — there is no separate description; the Spec covers it), **Design** (how, as settled so far), **Acceptance criteria** (how to tell it is done) and **Notes**. Stored in `task_agentic_briefs`, one row per Task that has one, and **kept whatever the flag says**: the flag can come and go with an ancestor's, and a brief written once is not thrown away by an edit two levels up. It is shown while the Task reads as Agentic — in the Task editor's Advanced section, the Agentic control followed by a **Brief** section — **collapsed by default** inside Advanced, its header saying the priority and whether a Spec is written, so the editor scrolls past it; it opens with a click or from the keyboard — and the MCP returns it with the Task (`agentic_brief`). Duplicating a Task copies it. **Templates and occurrences** (ADR 0008): a Task template — a flow task item, or the root of a task-instance flow — carries a brief of its own (`template_agentic_briefs`), edited in the flow item editor's Advanced section beside the template's Agentic control, and every occurrence **reads it field by field** until its overlay (`task_overlays.brief_*`) says otherwise — an occurrence can rewrite its Spec and keep reading its template's Design. A plain Flow's `start` copies the template's brief onto the Task it makes.

**Spec before start.** A Task that reads as Agentic **cannot be started** — moved into In Progress or **Started** from To Do or Done — while its brief has no Spec (whitespace is none). The move is **refused out loud** wherever it is made: the status control and `Enter` in every view (a toast naming why), the Task editor's save (the error line), and over the MCP, whose future status write goes through the same rule. A write to a Task already begun (In Progress or Started) is not a start, pausing and resuming included, so nothing already underway is stopped by it, and a write that supplies the Spec and starts the Task at once goes through. An explicit *Not agentic* under an agentic branch starts without one. The rule applies to a **Habit occurrence** the same way: one that reads as Agentic cannot be started without a Spec, its own or its template's. **Agentic is resolved one way everywhere, the way the app draws the tree**: a node's own flag; for an occurrence, its own value (its template's unless its overlay overrides it), then up its **template tree** — its parent item, the iteration's root (the Flow's own flag) — and then the Habit's host; and a stored row hung on an occurrence inherits from the occurrence, not from the host its columns name. The Spec rule, the agentic-wait rule and MCP write access all ask this one resolver (`tasks::agentic`), so an occurrence under an agentic Flow root reads as Agentic to all three, as it does on screen. **Creating** a Task is not a start either: the one path that creates one already in progress is a duplicate, and a copy of work underway is not the work starting.

**Asynchronous:** A Task can be marked **Asynchronous** — doing it starts a *wait* rather than finishing something. Send the email, order the part, kick off the build: do one of those first and the wait runs while you work on everything else; leave it to the end and the day is wasted. Nothing else in the model says which tasks those are.

It is a **plain boolean** (`asynchronous` — NOT NULL, default false), deliberately **not** the three-state inherited shape **Agentic** uses. The flag **does not inherit**, and with nothing to inherit there is no third state for an unset value to carry. The reason is the semantics, not the storage: "starts a wait" is a property of one concrete action, and a subtask of an asynchronous Task is usually the work you do *after* the wait — inheriting would flag exactly the wrong rows. **Tasks only**, on the narrower version of the Agentic argument: only a Task is *done*, and only doing it starts a wait. It is **independent of Blockers and Dependencies**, which model the wait itself.

**Expectation template** (settled by the user, 2026-09-23; `task_async_templates`, migration 0044). An asynchronous Task may carry an optional template of the wait finishing it starts. It exists **only while the flag is on** — turning Asynchronous off removes it — and a Task that is asynchronous **without** one is exactly what every asynchronous Task was before: it spawns nothing. So the migration moved no data. The template is thin: **title, tags, a Time Scope rule and Check every**, and **no status** — a template is never pending or released, only the wait drawn from it is. The Time Scope rule is a count (N days, weeks, months or seasons) resolved from the day the wait begins.

**The spawned wait is derived, never stored.** While an asynchronous Task with a template is **done**, a **virtual Expectation** hangs beneath it, in the spirit of ADR 0008: it exists because the Task is done and has a template, and for no other reason. Its title, tags and Check every are read from the template **as it is now**, and it begins when the Task was completed — `tasks.done_at`, which the Task's own status change writes and clears (tasks already done when migration 0044 ran carry the migration's time). **Reopening the Task, or undoing its completion, simply stops the wait being derived**: there is no extra write, no cascade and no special undo handling, because nothing but the Task's own row changed. The only stored state is the wait's **overlay** (`spawned_waits`: released, archived, last check), keyed by the Task and written only when the wait itself is changed; a wait nobody has touched has none, and reads as pending and live. When the wait stops being derived, the overlay row is **left where it is and ignored**, so completing the Task again brings its state back and redo is trivially correct (chosen over keying it by completion, which would have needed the completion as a key and made a re-completion start fresh). The same holds for everything written to the wait itself: its `expectation_overlays` row (its own title, window, Check every, Starting, privacy and agent fields) and its tag differences in `derived_tags` are keyed by the Task, not by the completion, so un-completing the Task leaves them where they are and re-completing it brings the wait back as it was edited — released or archived, retitled, retagged, and with its own Starting if it was given one, even one that is now past. Only its checks are per completion: one made before the Task was last completed does not count toward the current completion's schedule. A wait under a Habit occurrence behaves the same way (`occurrence_spawned_waits`, and its overlay row, stay put). What removes them is the Task itself going: deleting a stored Task deletes its waits' overlay rows and tag differences, and deleting a Habit, or the template item an occurrence is drawn from, deletes its occurrences' waits' overlay rows. A check made during an earlier completion does not count toward the current one's schedule. It is served as an **Expectation row** of the virtual table ([Derived nodes](virtual-nodes.md), `origin` `spawned_wait`) and is a **full Expectation node** (ruled by the user, 2026-09-26, per `Arlesh-pnn`): every view draws, releases and checks it as it does a stored wait (`Enter` and the glyph), and `E` on it opens the ordinary **Expectation editor** with every field a stored wait's editor offers — title, status, Time Scope, Check every and its Starting, tags, archive, privacy and the agent fields. What its template says is what it is **drawn with**; an edit lands in **that wait's own overlay** (`expectation_overlays`, its tags as differences in `derived_tags`), exactly as an edit to a Habit occurrence does, so the template — and every other wait it draws — stays as it is, and a field set back to the template's value follows the template again. Its status and archive are its own state from the start (`spawned_waits`). Only what its origin fixes differs: it cannot leave its Task (a move is refused out loud), and it cannot be deleted, copied or pasted (each refused out loud). **It has no Plan and takes none from its Task**: its Task's Plan does not show in its editor, does not bound what is planned beneath it (a check task), and does not hide it or its check task under Start — a wait cuts the Plan chain as it does for any Expectation. *Superseded:* `E` on it once opened the **Task's** editor, where its template lives, and then (briefly, in #94) an Expectation editor with the template-drawn fields locked; the user ruled both out on 2026-09-26.

**Dependents are not held up by it** (ruled by the user, 2026-09-23, "for now"): a Task depending on an asynchronous Task is unblocked when that Task is done, as it always was. The spawned wait is something to keep an eye on, not an edge.

**The spawned wait.** Completing an asynchronous Task spawns a **virtual Expectation** beneath it, in the spirit of ADR 0008: nothing about it is a row of `expectations`. Its title, tags and Check every are drawn from the template **as it is now**, under whatever the wait's own overlay says; its own state lives in a narrow **overlay keyed by the Task** (`spawned_waits`: when it began, status, archive, the last check), and it is served as an Expectation row (`origin` `spawned_wait`). **Un-completing the Task stops the wait being derived** and deletes nothing: its state and its overlay are kept and ignored, so completing again brings the same wait back with them (see above). Removing the template draws nothing from the overlay, and nothing blocks on it. A spawned wait is released, archived and checked exactly like a stored one (`Enter` and the glyph), but it cannot be deleted, copied or pasted (each refused out loud), and `E` on it opens the full Expectation editor, its edits landing on that wait alone (see above). Tasks already done when migration 0044 ran spawned nothing.

**A dependent waits on the spawned wait** (the conservative choice, flagged for the user): a Task depending on an asynchronous Task is blocked until that Task is done **and** its spawned wait is released, with the reason `"Blocked by expectation spawned by task {id} ({template title})"`. Doing an asynchronous Task starts something, so what depends on it depends on what it started.

Set from a **switch in the Task editor**, beside the Backlog switch rather than down in Advanced: it is a statement about the order the work wants to be done in, which is the same kind of question as whether the Task is set aside at all. While the switch is on, an **Expectation section** follows it with the template's fields; left empty, there is no template and nothing is spawned (a template with anything in it but a title takes the title "Waiting on {task title}"). It is also set from the bare **W** binding ("wait") in the Mindmap and List View, a plain two-state toggle of the Task's own flag — unchanged, and turning it off drops the template with it. **`Shift+W`** has the one distinct role left to it: on a Task it opens the **Task editor at its Expectation section, with Asynchronous switched on** — staged like every other field, so Cancel writes nothing. It shows as its own **status-row badge** (an hourglass, distinct from the Time Scope clock: a clock is a window that passes on its own, an hourglass is a wait somebody started) in both views, on the flagged Task alone and never on its children; and it is filterable as its own List View pill dimension (Asynchronous / Not asynchronous, with the usual Any/All/Exclusion modes), which reads the flag. Duplicating a Task copies both — the copy is the same action, so it starts the same wait. Sorting by it is a **List View** setting and opt-in; see [*List View*](list-view.md). *Superseded:* two settings, off by default, used to open the new-Expectation editor when a Task was marked asynchronous and offer it when one was finished; the template replaced both, so they are gone rather than kept as a second path.

**Time Scope & Plan:** A Task carries a **Time Scope** (relevance window) and an optional **Plan** (a single scope it is scheduled into). Goals carry a Time Scope but no Plan. See [*Time Scopes & Planning*](time-scopes.md).

**Backlog:** A Task may be put in the **Backlog** — deliberately set aside, not in play now, kept for later. It is the Task-side answer to what **Frozen** already does for a Goal or Project, and it is a stored **Archival** value (`live` / `backlog`) rather than a fourth status: status keeps meaning *where the work stands*, Archival *whether it is in play at all*, so a backlogged Task that was In Progress still says so when it is pulled back, and the Enter status cycle is untouched. **Frozen** stays Goals/Projects-only and **Backlog** Tasks-only; they are separate states and neither maps to the other. A backlogged Task is hidden from **Plan** and **Start** together with its whole subtree, shown under **All**, browsable on its own through the **Backlog** preset, and marked with its own status-row badge (not the Frozen snowflake). **Do shows it.** Backlog says *not planning this now* and Do asks *what is underway*, which are different questions a Task can answer yes to at once, so a backlogged In Progress Task still appears under Do rather than being hidden from the one preset that asks what is actually being worked on. **Setting a Task In Progress — or Started — takes it out of the Backlog**, which is where that tension is resolved: you cannot be actively doing something you have deliberately put down, so the status change clears the flag in the same write — one Gesture, so a single `Ctrl+Z` takes both back — and raises a **toast**, so it is never silent. The rule is one-directional and is *not* an invariant: backlogging a Task that is In Progress is still allowed and keeps its status, which is what lets it say where the work stood when it is pulled back. A request that names a Backlog state of its own alongside the status — the Task editor's Save — is taken at its word; the editor keeps the pair honest in front of the user instead, turning the Backlog switch off as **In Progress** is picked, exactly as it already does when a Plan is set. It is set and cleared from two places that mean exactly the same thing: a **Backlog** switch in the **Task editor**, as a switch rather than a status pill, since it is a separate axis from where the work stands — a backlogged Task keeps whatever status it had; and the bare **B** binding in the Mindmap and List View. The Goal editor has no such control and never gains one: a Goal is set aside by its own **Frozen** status. Backlog is deliberately *not* protective: a scoped backlogged Task whose window lapses unfinished still resolves **Missed** and archives, flagged as a conflict — see [*On-exit behavior*](time-scopes.md).

**Invariant: a Task is never both backlogged and planned.** Enforced at write time, asymmetrically, because the two directions differ in how much they throw away: backlogging a Task that has a Plan is **refused pending confirmation**, prompting with the option to clear the Plan and backlog in one action (declining leaves both untouched); setting a Plan on a backlogged Task simply takes it out of the Backlog, with no prompt — the gesture is unambiguous — and raises a **toast**, so the change is never silent.

A Task's **goal**, **project**, and **aspect** are resolved as the nearest ancestor of each type.

## Commitments

Commitments represent things that must be **kept** rather than **done**: an obligation or an abstention held over a window — "asleep by 23:00", "no social media today". Fields: title, parent (Project / Goal / Domain / Task / Commitment), Time Scope, **Verdict**, **Verdict Window**, tags (list), KB resource links, privacy, beads id.

A Commitment is its own content node kind, not a flag on Task, because its resolution runs the opposite way round: a Task untouched when its window closes is **Missed**, whereas a Commitment untouched may well have been **Kept**. A Goal is no better a home — it can be Achieved, Frozen or Archived, but has no vocabulary for having been *broken*, which is the single most important thing this kind has to record. See `docs/adr/0005-commitment-node-kind.md`.

**Verdict:** Unresolved / Kept / Broken. **Never derived** — not from the window passing, not from children completing. `unresolved` means only *you have not said*, which is real information that any defaulted verdict would destroy. Finishing every child Task of a Commitment therefore does **not** mark it Kept: credit is for the outcome, not for the sub-steps. Children's progress shows beside the verdict as a hint, and nothing more. A polarity field (abstentions default Kept, obligations default Broken) was considered and rejected on exactly this ground.

**Verdict Window:** how long past the end of its Time Scope a Commitment stays answerable — a **Duration**, a count of N of any scope kind, in the same `(n, kind)` form a Habit's **Gap** and a Time Scope's Duration take. Its kind is independent of the Commitment's own window, so a monthly commitment can be answerable for two days and a daily one for a week. Null inherits the nearest ancestor Commitment that sets one; nothing above setting one means it never expires, and there is no global default. Once `window end + N × kind` has passed with the Verdict still `unresolved`, the Commitment's effective **Archival** becomes **Archived** — still unresolved. **This is the only automatic state change in the kind, and it moves Archival, never the Verdict:** not having judged something is itself part of the record, and it stays visible under **All**.

**Lifecycle.** **Timing** (Pending / Active / Lapsed) reads the window alone, as for every other kind. **Resolution** is replaced by the Verdict. **Archival** is Live until either a verdict is recorded *and* the window has passed (the commitment is settled), or the Verdict Window runs out unresolved. There is no per-node On-exit behavior: a Commitment always Keeps, and the Verdict Window is what eventually ends that.

**Required scope.** A Commitment must have an **effective** Time Scope — its own, or inherited from a scoped ancestor. It is the first kind in the model for which being **Unscoped** is invalid rather than merely always-active: a rule held over no window has nothing to be kept or broken over, so one with no scoped ancestor at all is refused at write time. Inheritance is what makes this liveable — several of tonight's commitments sit under one scoped parent without repeating the window on each.

The rule is enforced at write time. A Commitment is created through its editor (`Shift+C`), which asks for the window up front and shows the refusal on the fields that would answer it (see [*Mindmap*](mindmap-view.md)).

**Children and the graph.** A Commitment holds Tasks (the supporting steps: "phone on charger", "set alarm") and other Commitments ("no social media this month" containing each day's), with the usual containment rule between a parent Commitment's window and a child's. It holds no Goals. It is **never scheduled** (the window *is* the commitment, so there is no Plan), and takes **no part in the dependency graph in either direction** — nothing gates it and it gates nothing. It is neither delegable nor blockable.

**Recurrence** rides the existing Flow/Habit machinery rather than a second engine: a Flow's **Instance Type** extends from `goal | task` to `goal | task | commitment`, so a nightly "asleep by 23:00" gets Recurrence and Iteration as they already are, and each night's verdict is a Modification row keyed by `(flow item, iteration scope)`. The clock is fixed to Window + Owed for commitment habits (Accumulating + Overlapping until the clocks replaced Consumption, Task #245) — **refused at write time**, not merely documented — because the Verdict Window is the bounding mechanism instead: under Archive a passed iteration classifies **Lapsed**, a derived "went unfinished" the kind forbids, under Overdue one unanswered night would be folded into the next, and an Interval has nothing to complete. The Habit's Verdict Window lives on the flow row (`verdict_window_n`/`verdict_window_kind`, migration `0028`), because a virtual iteration has no Commitment row to carry one and the Target Node is normally a Project or Domain, which carries none either. It is set in the flow editor, which offers the field only for a commitment Instance Type and clears it when the flow stops being one — a window on a goal or task Habit would be a value nothing ever reads. A commitment flow likewise has no **root Cycle Plan**: the window *is* the commitment, so there is nothing to schedule it into. An iteration whose Verdict Window has run out with no verdict recorded derives as **Expired**: archived, still unresolved, and never Missed. A commitment flow holds **no goal items** — a Commitment cannot parent a Goal, so such a template would derive no iterations at all: `create_flow_goal` refuses it, and a flow that already holds goal items is refused the switch to `commitment` rather than being allowed into that state and told about it afterwards.

## Expectations

An Expectation is a **wait**: something outside your own action that you are waiting on to be released, and may want to look in on — a model training run finishing, someone replying. It is not an action item: nothing about it is *done*, it is *released*. Fields: title, parent, status, archive, **Time Scope**, **tags**, an optional **Check every** with its **Starting** day, privacy. See `src-tauri/migrations/0042_expectations.sql` (and 0043, 0044). This section is about **stored** Expectations, made with `Shift+E`; the wait an Asynchronous Task with a template spawns is a virtual one, described under *Asynchronous* above, and works the same way wherever this section says it can.

**Placement.** Anywhere a Task can live — under a Domain, Project, Goal, Task or Commitment — drawn on the Mindmap and in the List View like any node. Its only stored children are **Info** notes; the one other thing that can hang beneath it is its virtual check task (below). It cannot be attached to a Habit occurrence — refused with a message; Arlesh-pnn's virtual node tables (ADR 0008) will make an occurrence an ordinary row that takes any child, which is where this comes from — and a Copy of one is refused on paste (a Cut moves it) — there is no duplicate command for it, as there is none for a Commitment.

**Agentic waits** — "the agent is waiting on you", the replacement for `bd human` (`Arlesh-cz2`, 2026-09-24). An Expectation carries a **separate agentic field**: a boolean and an optional **note**. An agentic wait is one an **agent raised on the Agentic Task it is working** when it needs something only the user can give — a decision, a credential, an answer — and the note carries its question. It may only hang **directly under a Task that reads as Agentic** — a stored one or a Habit occurrence, since an occurrence takes Expectation children like any Task; making one anywhere else is refused out loud (moving an agentic wait is checked the same way, but releasing or editing one whose Task has since stopped reading as Agentic still goes through, so a question can always be answered). The MCP raises one with `arlesh_waits` wherever it can write — an Agentic Task inside an MCP root (see [*MCP Server*](mcp-server.md)). **Question waits and waits on something else** (added 2026-09-25): an agent may wait on things other than the user, such as CI, so an agentic wait carries a **question** flag (`agentic_question`, default on) and an **answer** (`agentic_answer`), a text of its own beside the note, which stays the agent's question or context. A **question** wait is released **only with an answer** — refused out loud without one, from every release path (status control, `Enter`, a List row, the editor, the MCP); the wait's editor shows an **Answer** field for it. The user answers there; the agent may also release one itself with the answer it got from the user in its own session. A wait that is **not a question** is released without an answer, typically by the agent when the thing it waited on is done. The agent reads status, note and answer off the wait (`arlesh_waits.get`, or the snapshot). It is otherwise an ordinary wait: it shows wherever waits show, the **Expectations** preset lists it, and it wears the **bot head** in its status row — a question in the accent colour, the one badge that asks for something, with the question as its tooltip; a wait on something else in the muted colour, since it asks nothing of the user. It blocks nothing unless a Task is made to depend on it.

**Lifecycle.** **Pending → Released.** Released is what unblocks the Tasks depending on it; releasing again takes it back to Pending, so a misclick is undone by the same gesture. It can also be **Archived** — the usual archive, orthogonal to the status, so a wait that will never end can be put away without pretending it was released.

**Dependencies.** Only Tasks depend on an Expectation, and an Expectation depends on nothing. A Task depending on a **Pending** one is virtually blocked, with the reason `"Blocked by expectation {id} ({title})"` — the same mechanism a dependency on an unfinished Task uses. Deleting an Expectation deletes the edges aimed at it along with its notes: the edge column carries no foreign key, and a freed row id would otherwise be inherited by the next wait created.

**Check every** (settled by the user, 2026-09-23). Optional, with **no default**: a count of a kind — every N **days, weeks, months or seasons**, or, finer than any scope, every N **hours or minutes** (a Duration of kind `hour` or `minute`, counted by the wait's own rule rather than taught to every Duration) — and a **Starting** day, which defaults to now; a picked day means the **start of that Day**, 02:00 on the 02:00 → 02:00 ladder, not midnight (midnight is still the previous Day). Starting is picked with the app's own Day picker, which closes like the others — a click outside, `Enter` or Apply commits, Escape cancels; it replaced a native date input whose GTK calendar sat outside the page and could only be closed with Escape. The field has a **Clear** that returns it to no checks, and the save writes the NULL across IPC. It works as a **virtual Habit of check tasks**, and every check — hourly ones included — falls on the Day ladder. An **open "check on it" Task** exists beneath a Pending, live wait **only while a check is due**: from the instant the check falls due until it is completed — never before Starting — drawn on the Day it fell due, and titled `{prefix}{wait title}`, the prefix a display setting (default **"Check: "**, editable on the settings modal's Expectations page, an emptied field meaning no prefix). The first check is due at Starting (a spawned wait's, one interval after its Task was completed); completing a check — its status control or `Enter` on the check task — records it and the next falls due **one interval after that resolution**, not after the day it was due, so a check done late does not leave the next one already overdue. Completing a check that is not due yet is refused out loud.

**Completed checks stay** (ruled by the user, 2026-09-23). Each completion is stored — one row per check in `wait_checks` (migration 0045), keyed by its wait and the instant it fell due, with the time it was resolved — and **every** completed check stays beneath its wait as a **done** check task, filtered like any done Task: Plan, Start and Do hide it, All shows it. A check is **one node from due to done**: its id names its wait and the instant it fell due, so completing it keeps the node, and a selected check completed under Plan, Start or Do stays on screen, dimmed, under the focus exemption, as a done Task does, until the selection moves. (A first cut gave the open check a different id from the done one, so completing it lost the selection and it vanished.) All are drawn rather than only the latest — the conservative choice, since hiding is the presets' job and nothing is lost from view; a spawned wait draws only the checks of its Task's current completion. `Enter` or the status control on a done check **reopens** it: its row is deleted, it is the check due again, and the one after it — no longer due — goes. Only the **latest** completed check on a pending, live wait can be reopened; an older one is refused out loud, because the checks after it stand and it would have nowhere to be drawn. Undo and redo are the journal's own insert and delete of that row. The Expectation stays Pending throughout; releasing it means no more checks. A check whose Day passes uncompleted is **Overdue**, as a Keep-on-exit Task would be; nothing archives a wait for being late. A check task is a **Task row** of the virtual table ([Derived nodes](virtual-nodes.md), `origin` `check`), keyed by its wait and the instant it fell due: its status cycles like any Task's — To Do, In Progress, Done, Done recording the check and taking it back reopening it — and `E` opens its **own editor**, where it takes a title, Plan, flags, tags and block reasons of its own. Its day is when it fell due, shown in the editor but not changed, and it cannot be moved off its wait, delegated, deleted or copied — each refused out loud. *Superseded:* a one-off **check-by** window used to hang a single check task that completing cleared; stored check-by values were not migrated, since a single date has no interval to turn into one. The first cut of Check every drew the *next* check whenever there was one; the second made a completed check vanish; `E` on a check task used to open its wait's editor, and then — until checks became rows with Arlesh-pnn — to say it had none.

**Time Scope and tags, like a Task; no Plan** (settled by the user, 2026-09-23). A wait carries a **Time Scope** — its relevance window, set with the same field a Task's is and refused at write time if it escapes the nearest scoped ancestor's window, as a Task's is — and **tags**, in their own relation table, which the tag filters read as they read a Task's. Its window is its own: it does not inherit one, and an ancestor narrowing its window does not clamp a wait's (the descendant clamp still covers Tasks and Goals alone). A wait is never Missed, so a window that passes while it is pending makes it **Overdue**, and Start drops it as it drops a lapsed Task. Before its window **begins** it reads **Pending**, and Start drops it then too (ruled by the user, 2026-09-27). A wait with no window of its own also reads Pending while the window of what it hangs under has not begun — it is not in scope any more than that work is — but it is never Lapsed or Overdue for that window passing: it outlives the work it hangs under, as the spawned wait of a Task done yesterday is still waited on today. It is still **never scheduled** — there is no Plan, because you do not do a wait — and it has no beads id, no block reasons and no delegate. The Time Scope and Check every are separate: one is when the wait is relevant, the other when to look in on it.

**Presets.** A **Pending**, live Expectation shows under **All** and **Plan**, and under **Start** while its window is open — neither lapsed nor still ahead — **whether or not it has a Check every** — its check task, beneath it, answers the ordinary Task rules beside it. An app-wide setting, **Start hides waits that have checks** (Settings → General, **off by default**; ruled by the user, 2026-09-26), restores the older reading: with it on, Start shows a wait only when it has **no** Check every, the check task then being the thing to start. It applies to stored and derived waits alike, in every view and in the MCP snapshot's `filter` (`start_hides_checked_waits`). *Superseded:* Start always hid a checked wait, until the user saw a spawned wait checked every hour vanish from Start and made the rule optional. A wait whose window has **not begun** is hidden under Start **together with its check tasks**: its checks keep falling due on their own schedule — a check starting today on a wait whose window opens next week is due today, and every other preset shows it — but Start does not show one while its wait is not in scope yet. (Before 2026-09-27 Start dropped only a lapsed wait, so a wait due to open in two weeks showed there, check and all.) **Do** and **Backlog** hide it. A **Released** or **Archived** one shows under **All** only (the Archived pill's Include still force-shows an archived one). The List View has a dedicated **Expectations** option that shows every pending, live wait and nothing else; see [*List View*](list-view.md).

**Asynchronous Tasks.** An **Asynchronous** Task's wait is not a stored Expectation: it is the virtual one derived from its template while the Task is done — see *Asynchronous* under Tasks. A stored Expectation a Task depends on through an ordinary dependency edge is still possible, and is the way to wait on something no Task of yours starts.

**Keys** (settled by the user, 2026-09-23). **`Shift+E`** creates one under the selection, in the Mindmap, the Steps View and the List View (where it opens the editor, since a row has no inline title to fill). **`Shift+W`** on a selected **Task** opens its editor at the **Expectation** section with Asynchronous switched on (see *Asynchronous*); on anything but a Task it is refused out loud. `Enter` (`Space` in Steps) and a click on its glyph release the selected wait or take the release back, and the same on a check task complete the check or reopen the latest done one. *Superseded:* `L` (release) and `D` (complete the check) were bound too; the user removed them on 2026-09-24 as mere proxies for `Enter`, to keep the letters free.

**Glyph** (settled by the user, 2026-09-23). A **loading spinner standing still**: short radial ticks, all the same weight with round caps, evenly spaced round a circle and running clockwise from six o'clock, with a few left out at the lower right so the ring stays **open**. The ticks are **short**, leaving the centre open. At full size it is **20 ticks on 24 positions** (a gap of four); below a 16px radius — every Mindmap node and row icon today — it thins to **10 ticks on 12 positions** (a gap of two), heavier, because twenty ticks a few pixels apart blur into a grey ring. It shows **status only**: **Pending** is the tick ring; **Released** is the same ring with a **check inside**, one family, and never a Task's glyph, whose rings are whole lines. **Archival is not a glyph state**: it is stored separately from status and shown the way every other kind shows it — the node dimmed on the Mindmap and in Steps, and the archive badge in every view (the List View badges without dimming, as it does a Task) — so a pending archived wait is a dimmed tick ring and a released one a dimmed ring with a check. Spawned waits follow the same rule. Monochrome in the node's glyph colour, never animated. It stays clear of the status row's hourglass (Asynchronous) and clock (Time Scope) badges. *Superseded, in order:* a "loading ring" with a quarter open (with a solid disc for Released and a struck-through ring for Archived); a ring half solid, half evenly dashed; a solid top arc over shortening dashes.

## Beads id

A Task, Goal, Commitment or Project may carry an optional **beads id** — the identifier of the issue tracking it in `bd` (beads), e.g. `Arlesh-5fs`. It is a mirror of an id `bd` owns, not a value this app authors, and so is **write-restricted**:

- The **MCP server is the only source**. Each resource operator exposes a single setter (`set_beads_id`); `UpdateTaskRequest` / `UpdateGoalRequest` / `UpdateCommitmentRequest` / `UpdateDomainRequest` have no field for it, and no gesture can **author or edit** a beads id from the UI. Two named exceptions write the column from the UI side, and neither can produce a value `bd` did not issue.
- **Exception one: duplication.** Copy+Paste's `duplicate_*` commands *propagate* the id a node already carries onto its copy — only ever a value `bd` issued and the source already had. A source with no link produces a copy with no link. The accepted consequence is that two nodes can show the same issue id, and `bd` holds no record of the second.
- **Exception two: clearing.** Authoring and editing need a value the UI has no way to obtain; **dropping** a link needs none, and a link to a closed, wrong or duplicated issue otherwise has to go back through MCP to remove. One dedicated command, `clear_beads_id(node_type, node_id)`, writes null and nothing else — mirroring the MCP tool's shape rather than adding a field to any update request, and called by the editor's **Save** rather than by the × itself. Only `task`, `goal`, `commitment` and `project` are accepted, and a Domain that is not a Project is refused as it is on the way in. Nothing is told to `bd`: the issue is untouched, and this only removes Arlesh's mirror of the link.
- Every read that returns a Task, Goal, Commitment or Domain carries it.
- The UI shows it **read-only but for its ×, only where it is set** — as the **Issue** row in the Task, Goal, Commitment and Project editors, directly under the title. A node with no beads id shows no row at all: no label, no placeholder.
- The **×** takes no confirmation dialog, but it does not write either: it **stages** the clear, which **Save** performs and Cancel, Escape or closing the editor discard along with every other unsaved field. An earlier draft had it write straight through, on the reasoning that one nullable column is not worth a confirmation and `Ctrl+Z` puts the link back anyway. That was revised in use: the argument was about *confirmation*, and it silently answered a second question — whether this one field escapes the form the other fields are held in. It should not. Cancel means nothing was written, and a field that ignores it is worse than a field that asks.
- The clear is sent **before** the update it is saved with, so a refused clear leaves the node exactly as it was rather than half-saved, and the refusal appears on the editor's own error line with the editor still open. A clear that lands and an update that is then refused is the reverse case: the link is gone, the edits are not, the error says so, and `Ctrl+Z` reverses the clear. The clear is a Gesture of its own, so a save that also clears is two `Ctrl+Z`s — as a save that also retags or re-links is already several.
- The row **stays, greyed and without its ×, for the life of the editor** rather than vanishing: a dialog that reflows under the pointer hides the very thing it is reporting. Greyed means *staged*, not *gone*. Reopening the editor after the save shows no row, which is the steady state.

The column lives on `domains` for the Project case, but only the `project` subtype is given one and only a Project surfaces it; Aspects, Domains and Tags leave it null.

## Not built yet

Specced and kept, but not in the app today:

- **Delegation, beyond the Delegate itself and the Agent button.** No UI picks a Person as a delegate, a delegate does not inherit down the tree (the specced rule is an override, as Agentic's is, and it holds across kinds — see [*Link Inheritance*](link-inheritance.md)), and there is no delegate-to or delegated/undelegated filter (for how those treat the Agent, see [*Filtering Logic*](filtering-logic.md)).
- **Knowledge-base links.** Goals and Tasks list "KB resource links" among their fields, and the `goal_knowledge_base_links` / `task_knowledge_base_links` tables exist, but no command writes them and nothing filters on them.
- **Obsidian discovery.** People and Threads are meant to be discovered by recursively searching configured vault directories. Today they exist only as rows created through the backend commands.
