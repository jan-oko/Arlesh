# Mindmap (Tree View)

*One area of the [Arlesh design specification](../../SPEC.md).*

A canvas-based mind map editor. Layout: a **balanced tree** whose branches grow along one of two
orientations, toggled by the **Vertical layout** switch on the settings modal's Mindmap page and persisted with
the rest of the view state:

- **Horizontal** (default) — the first ⌈n/2⌉ of the root's children go right, the rest left.
- **Vertical** — the same split, rotated: the first half go down, the rest up.

Implemented with a custom SVG renderer using D3's tree layout algorithm. The orientation decides
which axis carries depth and which carries sibling spread; arrow-key navigation follows it, so the
branch axis always walks parent↔child and the other always walks siblings. Flipping the orientation
pans the canvas to keep the selected node (or the display root) in view.

The root of the map is "Arlesh" (top level). Aspect cells are its direct children.

**Keyboard interactions:**
- `Tab` / click — create a **Task** child, whatever the parent: `Shift+T` without the Shift. A parent that cannot hold a Task — a Tag, an Info note, an Expectation, a folded run of Habit history — **creates nothing and says why**, in the same toast `Shift+T` gives there, rather than falling back to another kind; every other kind is on its own `Shift`+initial chord. Inside a **Flow template** — the Flow or one of its items — `Tab` makes a **Task flow item**, exactly as `Shift+T` does there (see *Inside a Flow template* below). Until 2026-09-27 `Tab` there still added the template's next item of the parent's kind (a Goal item under a goal-instance Flow or a Goal item); the user ruled the same day that it too always makes a Task. Until 2026-09-27 the parent picked the kind: a Domain under an Aspect or a Domain, a Project under a Project, a Goal under a Goal, a Task under a Task, a Commitment under a Commitment, an Info under an Info, and `Tab` on a Tag was refused because its child would have been a Domain; the user ruled that the commonest key should always make the commonest thing
- `Shift+D` / `Shift+P` / `Shift+G` / `Shift+T` / `Shift+C` / `Shift+E` / `Shift+I` / `Shift+F` / `Shift+H` — create a child of a **named** kind under the selection (Domain, Project, Goal, Task, Commitment, Expectation, Info, Flow, Habit). `Shift+H` is a **Habit**: the same blank Flow editor `Shift+F` opens, with **Repeating** already switched on at the defaults the switch gives an existing Flow (see [*Habits*](habits.md#creating-a-habit)); it is parented, and refused, by a Flow's rules. `Shift+F`, `Shift+H` and `Shift+C` open an editor rather than creating a blank row, because those kinds are configured before they exist: a Flow (and so a Habit) by definition, and a Commitment because it **must** have a window, its own or an inherited one, and a rule that could never come due is not worth writing and fixing up afterwards. A parent that cannot hold that kind **creates nothing and says why** in a toast naming the rule — deliberately not climbing to the nearest acceptable ancestor, because putting the node somewhere other than where you pointed is worse than not creating it, while silence would read as a broken key. With **nothing selected** they do nothing at all, not even a toast. **Inside a Flow template** (the Flow, or one of its items) the chords make **flow items** rather than stored nodes: `Shift+T` a Task item and `Shift+G` a Goal item, under the same parenting rule a drag obeys (a Goal item hangs under the Flow or another Goal item, never under a Task item; a commitment Flow holds no Goal items, since a Commitment cannot hold a Goal, and says so). `Shift+C` and `Shift+E` are refused with a toast naming the kind — "Commitment can't be a flow item" — because a template holds Task and Goal items only (`flow_tasks`, `flow_goals`); the other chords keep their own kind and the parenting rule refuses them as anywhere else. Ruled 2026-09-27: the chords work normally inside a Flow but create flow items. The parenting rules are the same ones drag-and-drop and paste enforce, so the three can never disagree. `Shift+C` is free alongside bare `C` (centre on the selection) and `Ctrl+C` (copy), which strict chord matching keeps apart. The Commitment editor opens on a blank commitment with its Time Scope empty, whether or not a window is in reach: the chord behaves the same everywhere rather than branching on what the backend would have said. Saving with no window of its own and none above it is still refused, and the refusal shows **in the editor**, on the fields that would answer it, instead of closing on a save that did not happen
- Arrow keys — move between cells; with **nothing selected**, they pan the canvas instead
- `Shift+arrows` — extend the selection across siblings (on the sibling axis for the current orientation; on the branch axis they navigate as usual)
- `Alt+↑` / `Alt+↓` — move the cell among its siblings
- `Enter` — with a node selected: cycle a task's status / toggle a goal's achieved / cycle a **Commitment's verdict** (Unresolved → Kept → Broken → Unresolved) (double-tap enters a container as a subtree); **with nothing selected: focus the current display root**. A Commitment is both a container and a thing to judge, so it takes both: the single press cycles the verdict, the double tap enters its subtree, and the cycle waits out the double-tap window so that entering a commitment never records a verdict on the way in. Being blocked does not gate it — a Commitment is kept or broken, never worked on, and takes no part in the dependency graph
- `Alt+Enter` — on a selected **Task** (a Habit occurrence included), set it **Started** from To Do or Done, or flip In Progress ↔ Started; refused while it is blocked, as `Enter` is. Nothing on any other kind (see [*Tasks*](resources.md))
- `Shift+W` — on a selected **Task**, open its editor at the **Expectation** section with Asynchronous switched on: the optional template of the wait the Task spawns while done (title, tags, Time Scope rule, Check every). Staged like any edit, so Cancel writes nothing; it never creates a stored Expectation. Refused out loud on anything that is not a Task (see [*Expectations*](resources.md))
- **Expectations** take `Enter` and a click on the glyph, like any other node: on a wait it releases it or takes the release back (a delegated Task's wait refuses out loud — only the Task being done releases it); on a wait's check task it completes the check — records it, the next falls due one interval later, and the wait stays pending — or reopens the latest done one. There is no key of its own for either: `L` and `D` were removed by the user on 2026-09-24 as proxies for `Enter` (see [*Expectations*](resources.md))
- `X` — on a selected **Commitment**, mark it **Broken**, or clear the verdict if it already reads Broken. The same key it has in List View, so Broken is one press on both surfaces rather than two on the canvas
- `Shift+Enter` — create a sibling cell (a Task sibling carries over the source Task's **own stored** Agentic flag — see [*Tasks*](resources.md)); `Ctrl+Enter` — insert a parent above
- `F2` / `R` — rename the selected cell
- `E` — open the selected cell's editor; `Double-click` does the same
- `B` — put the selected Task in the Backlog, or take it out (any Task row, a Habit occurrence included; a wait's check task has no row to set aside, so the binding is inactive on one rather than silently doing nothing)
- `V` — switch the selected Task's **Compound**: whether it consists of its sub-items, its status derived from its subtree (stored Tasks only; a Habit occurrence is refused with a toast). Switching it off keeps the status it showed. Bare; `Ctrl+V` stays Paste — see [*Compound*](resources.md#compound)
- `W` — toggle the selected Task's **Asynchronous** flag: whether doing it starts a wait ("wait"; real Tasks only, on the same reasoning as `B`). A plain two-state toggle — the flag does not inherit, so what the badge shows is what the column holds and one press flips both. Turning it off drops the Task's Expectation template. Bare, beside `A` and `B`, and bound to nothing else in either view — see [*Tasks*](resources.md)
- `A` — toggle the selected Task's Agentic flag: whatever it reads as now, one press writes the opposite (**Agentic ↔ Not agentic**); *Inherit* is resolved through, never written, so returning a Task to it means opening the editor (real Tasks only, on the same reasoning as `B`). Bare letters are flags on the selected Task, `Alt`+letter is a status preset, so `A` and `Alt+A` (the **All** preset) coexist exactly as `B` and `Alt+B` do — chord matching is strict about modifiers
- `P` — set the selected Task's **Plan** in a quick picker drawn at the node, without opening the editor: the editor's own Scope Picker and write, so every Plan rule applies and one `Ctrl+Z` takes it back. A multi-selection is planned whole, in one Gesture; a node that holds no Plan is refused by name. See [*The quick Plan picker*](time-scopes.md#the-quick-plan-picker-p). Bare `P` only: `Shift+P` creates a Project, `Alt+P` is the Plan preset and `Ctrl+P` the Plan View
- `D` — make the selected Task **depend on** a Task, a Goal or an Expectation, picked in a small search bar drawn at the node, without opening the editor. It leaves out the Task itself, what it already depends on and anything that would close a cycle; one `Ctrl+Z` takes it back. A node that cannot depend on anything, and a multi-selection (ruled by the user, 2026-09-29), are refused out loud. See [*The quick dependency picker*](resources.md#quick-dependency). Bare `D` only: `Shift+D` creates a Domain and `Alt+D` is the Do preset
- `Delete` — delete the selection. A **Habit occurrence** goes through the same confirmation as any node, and its delete archives that one repetition ([Derived nodes](virtual-nodes.md)). A drawn node with no row — a folded run, a wait's check task — is refused out loud, *before* the confirmation, not inside it: a dialog whose only possible outcome is "delete failed" is worse than no dialog. One such node anywhere in a **multi-selection refuses the whole gesture**, rather than deleting the real nodes and naming what was skipped the way paste does: a delete is destructive where a paste is additive, and the notice would be raised underneath the confirmation's own overlay and fade unread. Adjust the selection and press again. An **Aspect** is refused on the same terms: the six are seeded with the board, the backend refuses every write to one, and there is no gesture anywhere that removes one — so `Delete` on an Aspect alone says why instead of doing nothing, and an Aspect in a multi-selection refuses the whole gesture instead of being quietly dropped from the delete set
- `Ctrl+/` — collapse or expand the selected cell, including opening and re-folding a Habit's collapsed history (see *Habits*)
- `Ctrl+Alt+/` — collapse or expand the selected cell **and everything beneath it**, all the way down, in one press: the recursive counterpart of `Ctrl+/`. It reaches both kinds of closed cell in the same walk: an ordinary collapsed cell stops being collapsed, and every node the Habit fold drew — the run and each scope level inside it — is opened (see *Habits* for why those are two sets and not one). Which way it goes is read off the selected cell alone — shut opens, open shuts — so a second press undoes the first and the board comes back to where it started. Each kind keeps its own persistence rule, so the fold's openings survive a restart with the tab and the ordinary expansions do not. It is on `Ctrl+Alt` rather than the `Ctrl+Shift+/` that would read as "more of `Ctrl+/`" because the cheat-sheet has held that chord since it shipped. Two bindings can share a chord only when their guards are exactly complementary, and these two sit in different tables dispatched by different listeners, so nothing orders them and the split would have to be maintained by hand in two places at once — while any guard on the cheat-sheet is a state in which the shortcut list is unreachable. `Ctrl+Alt` was unused across every binding table, and a free chord beats a shared one
- `Ctrl+X` / `Ctrl+C` / `Ctrl+V` — cut / copy / paste
- `C` — center the view on the selection; `Ctrl+=` / `Ctrl+-` (and numpad `+`/`-`) — zoom
- `S` — start the selected Flow; `F` — convert the selected cell to a Flow, or, with **nothing selected**, show the board alone *(see [Tabs](tabs.md); `F11` is the global form)*
- `Ctrl+O` — search for a node by title *(a [global binding](tabs.md) — declared once, not per view)*; archived nodes are left out unless Settings says otherwise (see [*Archived nodes in search*](#search-archived))
- `Alt+F` — toggle the [Filter menu](#filter-menu); `Ctrl+F` — the [filter search](#filter-search) *(both [global bindings](tabs.md) — declared once, not per view)*; `Alt+A` / `Alt+P` / `Alt+S` / `Alt+D` / `Alt+B` — jump to the **All / Plan / Start / Do / Backlog** status preset (matched by physical key)
- `Escape` — deselect (this one stays per view: only a view knows its selection); `Shift+Escape` — go back one level when inside a subtree; `Ctrl+Escape` — go back to the root *(a [global binding](tabs.md) — declared once, not per view)*
- `Ctrl+Z` — undo the last thing you did to the board; `Ctrl+Shift+Z` (or `Ctrl+Y`) — redo it
- `Ctrl+L` — show the List View, `Ctrl+P` the Plan View, `Ctrl+S` the Steps View, `Ctrl+J` the [Zen View](zen-view.md), `Ctrl+M` the Mindmap (one chord per view, not a cycle — see [*Tabs*](tabs.md)); `Ctrl+Shift+/` — open the keyboard cheat-sheet; `Ctrl+Q` — quit *(global bindings, as are the [tab shortcuts](tabs.md))*
- `Right-click` — context menu (enter subtree, change type, delete, etc.)
- The top bar's subtree **breadcrumb** is the pointing-device equivalent: every ancestor segment exits to that level

A shortcut requires exactly the modifiers listed — `Ctrl+E` does not open the editor, only a bare `E` does. Every binding above is declared once in the shared hotkey registry (`src/utils/hotkeys/`), which is also what the cheat-sheet renders, so this list, the overlay, and the handlers cannot disagree. The view-level bindings (Mindmap, List View and Plan View) are suppressed whenever a modal or an inline rename is on screen; the global ones (`Ctrl+Shift+/`, `Ctrl+Q`, `F11`) always stay live, while the view switcher (`Ctrl+M`/`Ctrl+L`/`Ctrl+P`) is suppressed along with them. That suppression is driven by the modals and inline editors themselves, each registering while it is mounted (`src/stores/use-input-capture-store.ts`), rather than by the views tracking which of their own state flags imply an open modal — a flag can outlive the UI it describes, and a stale one would silently kill every view binding until the view remounted.

**When a gesture cannot act.** Three answers are possible, and which one applies is a rule rather than a per-gesture choice — the three drifted apart once already, and a user cannot learn a surface where the same non-answer means three different things.

1. **Refuse out loud.** The default, and what nearly everything is. The gesture was aimed at a node and the node cannot take it: a toast names the node's reason and, where the rule has a positive form, where the thing *would* go — so it answers "then where?" in the same breath. This covers both halves of a refusal: a rule the app knows in advance (a Goal under a Task, an Aspect, a Habit repetition) and a refusal the **backend** raises after the write is sent. Every gesture that writes ends in a catch that says what failed and appends the backend's own reason; a `console.error` alone is a note to the developer, not an answer to the user, and a board that silently did not change is worse than a wrong reason or a generic one.
2. **Inert, and declared.** A binding may do nothing at all only where nothing was aimed — no selection, an empty clipboard, an id that has left the tree, the synthetic root — or where the binding is **declared inactive** for that node in the shared hotkey registry, so the cheat-sheet says so. `B` and its neighbours on a virtual Habit occurrence are the declared case. An `if (…) return` inside a handler is not a declaration and does not qualify: an inert key is indistinguishable from a dead one.
3. **Silently drop.** Never. Acting on part of a selection and saying nothing about the rest is the defect this rule exists to forbid.

A **drag** is the one gesture that answers by not answering, and legitimately: it refuses by not lighting the node up, which is on screen continuously while the pointer is over a target that would not take the drop, where a keystroke's refusal has no such moment. It must therefore never *offer* a drop the write cannot make.

**One gesture, one message.** The view holds a single pending toast — a slot, not a queue, and it stays one: a queue would leave the user reading notices about a gesture that finished two gestures ago, and the second call would in any case overwrite the first. So a gesture with several things to say composes them into one message: a paste names every reason it skipped something, and a delete refused for two reasons says both. A message the same gesture raises **later** — a backend refusal arriving after a skip notice — replaces the earlier one only by **containing** it, carrying both sentences, so nothing the gesture said is taken off screen unsaid.

**A mixed selection** is decided by the cost of being wrong. An **additive** gesture acts on the rest and names every skip: that is paste. A **destructive** one refuses the whole selection and acts on nothing: that is delete. Refusing a delete costs a keystroke; acting on half of one costs data. The notice could not be read beside the confirmation anyway — the toast sits well below the modal's overlay and fades while it is covered — so "deleted the rest, mentioned the skip" would be a silent skip wearing a message.

**A node, not a kind.** Whether something can hang under a node is asked of the **node**, never of its kind alone. A kind cannot tell a real row from a drawing of one, and three nodes on the canvas wear a kind that would otherwise say yes: the synthetic root, a **folded run of Habit history** (a tally and a span standing in for many iterations), and a **Habit occurrence**. An occurrence is a row ([Derived nodes](virtual-nodes.md)): it holds children of its own — created there, or moved there by cut and paste or a drag, each hung on that one iteration — and takes anything its kind takes except a Flow or a flow item, which belong to the template it is a repetition of. Nothing is *copied* onto it, since a copy is a stored row made under a stored parent. A folded run and the root hold nothing. The kind rule underneath is **exhaustive**: a kind it has not been taught about is refused, not permitted, so a new node kind arrives unable to parent anything rather than able to parent everything — which is how a folded run came to accept children in the first place.

**Modals and focus.** `Escape` dismisses any modal, and a modal is dismissable the instant it appears — so every modal **takes focus when it opens**, because dismissal is handled on the dialog element itself and a dialog holding no focus would not hear the key until the user tabbed or clicked into it first. Where that focus lands is decided per modal, not by DOM order. An **editor** focuses its own first field and selects its contents, so typing replaces the title rather than appending to it. A modal that exists to be **answered** focuses the answer that is safe to give by reflex: `WarningConfirmModal`, the convert-to-flow prompt and the commitment-window prompt focus **Cancel**, so the consequences are read before anything acts on them, while `DeleteConfirmModal` focuses **Delete**, the one case where the answer is known before the modal opens and confirming should stay a single key. Opening focus never lands on a toggle, where a reflex `Space` would change a stored setting instead of dismissing the dialog.

**Entering a subtree:** Right-clicking a cell and selecting "Enter" re-roots the map at that cell; `Ctrl+O` does the same from the node search, in either view. Navigation back: any ancestor segment of the top bar's **breadcrumb** — including the middle of a deep chain, which the keys cannot reach in one step — `Shift+Escape` (up one level), or `Ctrl+Escape` (straight back to the root).

The subtree root is **shared between the Mindmap and the List View**, not per-view, and **owned by the tab** rather than by the app: entering a subtree in one view and switching to the other leaves you in the same place — the same reasoning that makes the two views share a tree and a filter rather than drifting apart — while every other tab stays exactly where it was. The List View honours it by flattening from the subtree root's **children**, so it lists exactly the Tasks beneath it and the subtree root is **trimmed out of the path headers entirely** — inside `CODE`, a header reads `Goal Alpha`, not `CODE › Goal Alpha`. Where you are is named once, by the top bar's breadcrumb, instead of being repeated on every header. Trimming happens by scoping the *walk* rather than editing the paths afterwards: a row's ancestors are just the nodes stepped through to reach it, so the root is never collected in the first place and a header's `segments` and a row's `visibleDepth` go on partitioning those ancestors exactly — an after-the-fact trim would leave the indentation claiming a parent the header no longer names. One consequence: a row whose only ancestor *was* the subtree root now has an empty path and gets **no header at all**, the same handling a task with no ancestors already gets at the true root.

Because the top bar holds no tree of its own, whichever view is mounted resolves the descriptor for it (`src/hooks/use-subtree-nav.ts`) — the chain of ancestors above the subtree root, and the title of the root itself — so the breadcrumb is correct in both views, rather than only in the one that happens to own the subtree logic. It is the single answer to "where am I": the bar consumes it and derives nothing of its own, which is also what the tab's label is taken from.

**Status-icon row:** below each node sits a compact row of status badges (aligned to the node's left edge), each with a hover tooltip. A **clock** marks a Time Scope (tooltip = the window; crossed out once the window has passed); an item carrying the **Overdue** flag (past the end of its due; see [*Time Scopes*](time-scopes.md#due-scope-and-the-overdue-flag)) gets **no badge** — its amber node border says it (the red exclamation that used to flag it was removed on 2026-09-30, "border is enough"). A node **both selected and Overdue** takes a selection border of its own, `--overdue-selected` — a brighter amber in the dark theme and a vivid orange in the light one, apart from both the ordinary selection accent and the unselected amber — so it still reads as the selection without losing the one sign that it is Overdue (ruled by the user, 2026-09-30, and since carried to every view — see [*Due scope and the Overdue flag*](time-scopes.md#due-scope-and-the-overdue-flag)); a drop target's accent wins over the amber while dragging (see [*Due scope and the Overdue flag*](time-scopes.md#due-scope-and-the-overdue-flag)); an **archive box** any item whose *effective* Archival is **Archived** — an explicitly-Archived Goal/Project, or any scoped Task/Goal whose Resolution is **Completed** or **Missed** — tinted as a warning when it's a **conflict** (a manually-Frozen item that scope forced into Archived); a **calendar** marks a Plan (tooltip = the plan window); a **snowflake** a Frozen goal/project and a **tray** (three stacked lines) a Task in the **Backlog** — a badge of its own, since Backlog and Frozen are distinct states, and one that can appear alongside the archive box when a lapsed window has forced Archived over it; a small **bot head** marks a Task that reads as **Agentic** (see [*Tasks*](resources.md)) — its own flag or an ancestor's, since a branch marked in one edit must look marked all the way down; an **hourglass** a Task marked **Asynchronous** (see [*Tasks*](resources.md)) — its own flag and never an ancestor's, since the flag does not inherit, and an hourglass rather than a second clock because a clock is a window that passes on its own where an hourglass is a wait somebody started; **no badge carries a Commitment's Verdict** — the node glyph itself does (see [*Commitments*](resources.md): hollow while the answer is owed, solid once given, cleft when broken, struck through once the Verdict Window has run out), so the row would be restating it a few pixels below; every badge here says something the glyph does not; an **ellipsis** an Info node carrying a Details description (tooltip = the text); a **wave** a real Start-flow instance and the **cyclical habit glyph** a virtual Habit iteration; a **tag** icon a node with tags (tooltip = their names); and an **antenna** — a filled emitter dot on one straight mast, with a signal arc either side radiating from the dot — a node the MCP can see — inside an MCP root and not private (tooltip = *Visible to the MCP (via {root})*; see [*MCP Server*](mcp-server.md), *Access*). The antenna reads as a connection out to the agent rather than as something watching, and is drawn as one line, a dot and two open arcs so it stays distinct from the wide, closed bot head beside it. It has one state: whether the MCP may also write the node is exactly whether it is Agentic, which the bot head already says, so a second "writable" badge would say it twice. A derived node takes its nearest stored ancestor's antenna. A **crossed-out eye** — an almond outline with a solid pupil, struck through by one diagonal from lower left to upper right — marks a node marked **Private** (tooltip = *Private*): its **own** flag and never an ancestor's, like the hourglass. Privacy does act on the whole subtree — outside Private Mode a private node is hidden with everything under it (see [Filtering Logic](filtering-logic.md)) — but that is a filtering consequence, not a state of each node beneath: the flag is set on one node, and badging the subtree would mark every row under it alike and hide which one holds the switch. There is no fainter inherited variant, because the row has no such convention — the bot head, the one inherited badge, is drawn the same whether the flag is the node's or an ancestor's. A derived row reads its own flag: a Habit occurrence its row's, a derived wait its overlay's. The struck-out eye was settled by the user (2026-09-27) over two closed-eye drafts: a lid arc with lashes, then an almond with a tinted lid. An eye rather than a padlock, because a lock would read as *locked* — read-only, or closed to the MCP — where the flag means *not shown*, and a lock's body would be one more small box beside the archive box and the calendar. It takes the antenna's place at the end of the row; the two never meet on one node, since the MCP never sees a private one. The same row, antenna and eye included, is drawn on List View rows and on Steps and Plan View cards. Badges appear only when relevant, so most nodes show few or none. **The layout reserves the row**: wherever nodes stack top to bottom — siblings in the horizontal layout, levels in the vertical one — each node is spaced by its drawn size, its wrapped title and, whenever it shows *any* badge, the badge row beneath it, so a row never lands on the next node; the fixed gaps stay the minimum, so small nodes sit exactly where they always did. (The row used to be left out of the spacing, which the MCP antenna exposed by giving many tall nodes their first badge.) The set of badges is a pure function of the node; scope/plan/tag tooltips resolve their labels on demand.

**Top bar:** sits below the tab strip and belongs to the **active tab** — every control on it reads and writes that tab. At the start edge, a settings **gear** that opens the **settings modal** (below); one **view tab** per view — Mindmap, List, [Plan](plan-view.md), [Steps](steps-view.md) and [Zen](zen-view.md); a **status-preset dropdown** (All/Plan/Start/Do/Backlog, plus a 6th **Unblock** option while List View is active — see [*List View*](list-view.md)) — a dropdown rather than a segmented control so it stays compact next to the tabs, built as a themed `Select` (listbox popover styled from the app's own tokens, with arrow-key/Enter/Escape keyboard support) rather than a native `<select>`, whose open option list ignores CSS and renders with plain OS chrome; **centred on the bar**, the subtree **breadcrumb** — `Arlesh › CODE › ARLESH › Features`, shown only inside a subtree and nothing at all at the true root. It is centred on the bar itself rather than on the space the two clusters leave between them: the start-edge cluster is several times the width of the Filter button, so that leftover space has its middle well right of the bar's. The two side columns are therefore given the same share, and fall back to their own content width only when a window is too narrow for an equal one. The middle column is held open at the true root too, so the Filter button does not move when a subtree is entered or left. It replaced three controls that said the same thing three times (an `↑`-to-the-root pill, a `←`-up-one-level pill and a centred indicator) and could not, between them, express the middle of a deep chain at all. Every **ancestor** segment is a button that exits to *that* level — the first is the true root, so it does what `↑` did — while the **last** segment is where you are, left as plain text with no pill, border or background, since "here" has nowhere to navigate to. It carries no glyph: the chain is the thing being read, and a marker in front of it competes with the titles it exists to qualify. Instead the `nav` is **named** — "Inside subtree" — so a screen reader announces the landmark for what it is rather than reading out a run of bare titles. When the chain outgrows the room the bar has left, its **middle folds into a `…`** whose menu enters any level it dropped, so nothing becomes unreachable; the levels nearest where you are are the last to go. **Whole segments go before any text is cut**, because a clipped title says less than a missing one the `…` still reaches: once the whole middle has folded, the order is `root › … › here`, then `… › here` (the root joins the menu), then `root › …` — only when *here* is too long to stand beside the `…` on its own, with its title on the `…`'s tooltip — and only when none of those fits does *here* truncate with an ellipsis, alone beside the `…`. Two titles are never cut at once, and a cut title never sits beside the root. Which levels fit is **measured, not counted** — title lengths and window width decide it, and the folding happens before the frame is painted, so an overflowing chain is never seen. What is measured is the cell, never the chain: a box that shrank onto its own content would report "fits" the moment a segment folded, hand the room straight back and fold it again for ever. The fit **follows the cell's width both ways**: as the window narrows — or a pane beside the bar grows — more of the middle folds, and as it widens again the folded levels come back, however narrow the bar was when the subtree was entered. Every change of width re-measures from the whole chain rather than from the folded one, so a level returns exactly when it fits. Each segment also truncates at its own fixed width cap, and the chain is clipped by the cell rather than running under the Filter button. `Shift+Escape` and `Ctrl+Escape` are unchanged and call the same two exits the segments do. And, at the end edge, the **agents' status** — a small bot head, shown only while agents are at capacity, an agent's wait is pending or Agentic work is In Progress (see [*MCP Server*](mcp-server.md), *Agent capacity*) — then a **Filter** button (funnel) that opens the [Filter menu](#filter-menu). Below the bar, a wrapping row of **active-filter chips** renders whenever any filter is engaged (empty and takes no space otherwise) — every active tag filter and, while List View is active, every active List-View-exclusive pill filter (see [*List View*](list-view.md)). A chip shows a mode symbol (∪/∩/∅) and the filter's name; clicking the chip body cycles Any → All → Exclude, and an embedded **×** removes it. A chip's border/symbol color is a muted accent for its mode — a fixed, low-key hue per mode shared across every dimension, blended most of the way toward the neutral border rather than shown at full strength; its background additionally tints toward the value's resolved aspect color where one exists (tags, Antecedent, Dependency).

A **keyboard cheat-sheet** overlay is available from that settings entry or with `Ctrl+Shift+/`: it lists every binding in the app, with the chords that share an action merged onto one row (so the four arrow keys read as a single `← → ↑ ↓` line). **Searching the cheat-sheet** (asked for by the user, 2026-09-30). A **search field** heads the sheet and has the focus when it opens, so typing narrows it straight away. When nothing matches, the sheet says so. **Clearing the search returns to the tab it was on**; clicking a tab during a search clears it and shows that tab. **Esc** empties a typed search first and a **second Esc** closes the sheet; with the field already empty, one Esc closes it as before.

**Mindmap filter:** prunes the displayed tree — a node is hidden unless it matches or has a matching **content** descendant (ancestors of matches stay, keeping the map connected). The **selected** node is exempt from all of it, together with the ancestor chain that reaches it, for as long as it stays selected ([Filtering Logic](filtering-logic.md)). Info notes are *attachments*: they ride along with a kept node but never keep one (an achieved goal whose only children are notes is still hidden). The **status preset** lives in the top bar (see above) — except in the Plan View, which always reads under **Plan** and draws the others disabled without overwriting the tab's own ([Plan View](plan-view.md#always-the-plan-preset)), and the [Zen View](zen-view.md#always-the-do-preset), which does the same under **Do**; the rest is in the **Filter menu** opened from the **Filter** button, described below the list:
- **Status preset** (single, in the top bar, not the popover): **All** · **Plan** (hide done tasks, achieved/frozen/archived goals, and anything else whose *effective* Archival is **Archived** — a Task or Goal a forced Resolution archived, regardless of its own stored status) · **Start** (Plan, minus in-progress tasks with no todo child, minus **Started** tasks while the app-wide *Start shows Started tasks* setting is off — it is on by default, minus Timing-**Lapsed** items — a strict superset of Plan's Archival exclusion, since it also drops unresolved **Overdue** items that Plan still shows — minus Timing-**Pending** items, minus Habit flow nodes, minus Tasks **planned ahead**; a **blocked** task/goal is dropped together with its whole subtree — it gates what's beneath it, so nothing under it is startable either). A Task, Goal or Expectation is **Pending** when its window — its own, or for a Task or Goal with none, its nearest scoped ancestor's — has not begun yet (see [*Time Scopes*](time-scopes.md)): what is not in scope yet is no more startable than what has left it (ruled by the user, 2026-09-27; before, Start dropped only the Lapsed side, and an Expectation with a window in two weeks' time showed under Start today). For a Task or Goal, like Lapsed and planned-ahead, it **fails the node's own match rather than gating its subtree**: a child with no window of its own reads its parent's and is Pending too, so it drops on its own account, while a child whose own window is already open still shows and holds its parent on screen as its ancestor. A **Pending wait gates its subtree**, taking its check tasks with it: a check is timed by the Day it fell due, not by the wait's window, so a wait checked on weekly from today has a check due today even though its window opens next week — the check still falls due and every other preset shows it, but Start does not while the wait is Pending. The Archived pill's Include still force-shows an archived one. A Task is *planned ahead* when its **Plan** has not begun yet — **now**, on the 02:00 day boundary (see [*The day boundary*](time-scopes.md)), is still before the Plan's window: a Task scheduled into next week is not something to begin now. Only a Plan still ahead hides. One that has **ended** unfulfilled leaves the Task visible as missed work — missing a slot does not make the work less startable, and the Task's own Time Scope, not its Plan, decides when it stops being relevant. An unplanned Task is unaffected. **Interim, pending Plan inheritance (`Arlesh-67y`):** a Task with no Plan of its own is read by its **nearest planned ancestor Task's** Plan, so the sub-steps of a Task planned for next week drop with it; a Task with a Plan of its own answers to that Plan alone, whatever its parent's says. The inheritance is this filter's reading only — nothing stored, edited or badged inherits a Plan yet. The rule fails a Task's own match rather than gating its subtree, so a sub-step with a current Plan still shows and holds its future-planned parent on screen as its ancestor. Expectations and their check tasks carry no Plan either, and a **wait cuts the inheritance**: a check task answers to its own due time, so a check due today stays under Start even when the Task its wait hangs under is planned for next week. Goals and Commitments carry no Plan and are unaffected, and so are virtual Habit occurrences: their Cycle Plans are not read, since whether an occurrence's window has opened is already the unopened-occurrence rule's question (see [*Habits*](habits.md)) · **Do** (only in-progress tasks, and **Started** ones while the app-wide *Do shows Started tasks* setting is on — off by default; see [*Tasks*](resources.md)) · **Backlog** (the inverse of the others: only Tasks deliberately set aside, together with their whole subtrees — see [*Tasks*](resources.md); available in both views, unlike Unblock). **Commitments answer to their own branch of these rules**, because the kind resolves the other way round: **All** shows every Commitment including past verdicts; **Plan**, **Start** and **Do** show only the **unresolved** ones — what you have yet to judge is what is still live, and a recorded verdict, **Kept or Broken alike**, is answered the way a done Task is, whether or not its window is still open. (Plan used to keep a Broken commitment on screen while its window was open; the user ruled that out on 2026-09-23.) **Backlog** shows none, since a Commitment has no Backlog state to be in. **Expectations** answer theirs too: a pending, live wait shows under All and Plan, and under Start while its window is open (neither Pending nor Lapsed), whether or not it has a Check every — only without one while the app-wide setting **Start hides waits that have checks** (Settings → General, off by default) is on, its check task then standing in for it; Do and Backlog hide it; a released or archived one shows under All only (see [*Expectations*](resources.md)). A **delegated Task** reads as archived under every preset (see [*Tasks*](resources.md)). In every filtered mode, structural containers (Aspect/Domain/Project/Tag) appear **only as ancestors of a content match** — an empty or fully-resolved container drops out — **except** in Plan, where an **active** (non-resolved) Aspect/Domain/Project shows on its own so you can plan/create items in an empty one (resolved ones, and Tags, stay ancestor-only). Only a Project can be *given* a status, so a status-less container **inherits the nearest status-bearing ancestor's** status rather than reading as active: the Domains inside an Achieved or Archived Project are resolved along with it and stay ancestor-only, while those inside an Active one still show on their own. A container with no status-bearing ancestor at all reads as **Active**. A **Frozen** or **Archived** Project goes further in Plan/Start: it is dropped **together with its whole subtree** (like a blocked Task/Goal under Start), so unresolved work inside it doesn't hold it on screen — its status says the work is off the table, so nothing under it is plannable or startable either. **Achieved** is deliberately softer and keeps the ordinary ancestor-keeping: finished work can still contain unfinished items worth surfacing. The Archived pill's **Include** still overrides this for the Archived case. **All** shows everything, containers included.
- **Private Mode** — the **Private** switch in every view's Filter menu: off by default, and while it is off every node marked **Private** is hard-hidden together with its whole subtree (dropped outright, not kept as an ancestor); turning it on reveals them. Every node kind carries an `is_private` flag, set from its editor modal. Marking a **flow item** Private is a real stored field that also propagates to that item's instances — the virtual Habit instances inherit it, and starting a flow copies it onto the materialized Goal/Task (the flow root's flag propagates to the root instance likewise). The **Include flows** subtoggle (Mindmap only, shown under Plan/Start) is separate from the global Flow type toggle — both must be on for flows to show; the Info/Flow **node-type** toggles hide those subtrees and are drawn in the Mindmap only, since the List View's rows are Tasks, Commitments and waits.
- **Plan scope** (in the top bar, beside the status preset it belongs to, not in the popover — it moved out of the Filter menu on 2026-09-26, because a narrowing that changes the whole board should sit where the preset is read, not behind a button). Drawn only while **Plan** is the preset: in the Mindmap and Steps Views, and in the List View unless its own Unblock or Expectations option has replaced the preset's rules — never in the [Plan View](plan-view.md), which has a scope of its own and reads under Plan whatever this says. An optional scope, chosen with the app's own Scope Picker, which floats below the control — any kind, one cell — and cleared with **Clear** beside it; none is the default, reads *Any scope*, and narrows nothing. The control's hover says what the scope does under the current match. With one chosen, a **Task** shows under Plan only when its Time Scope is **relevant** to it, which by default means **contained**: the Task's window lies wholly inside the scope, an equal window included, and one that merely overlaps it is left out. Two readings were chosen here and are the user's to overrule: the window read is the Task's **effective** Time Scope — its own, or the nearest scoped ancestor's when it has none, as relevance is read everywhere else — and an **Unscoped** Task, with no window of its own or inherited, is contained in nothing and is **hidden**. A Settings switch (General — *Plan scope keeps Tasks that overlap it*) changes the match to **overlapping**: a Task shows when its effective Time Scope shares any instant with the scope (a window ending where the scope begins does not), and an Unscoped Task, which the model defines as always relevant, overlaps every scope and shows. The switch is app-wide rather than the tab's; the scope itself is the tab's and is kept with it. Only Tasks are narrowed — Goals, Commitments, Expectations and containers answer the preset as before — and the narrowing fails a Task's own match rather than gating its subtree, so everything else about a filter holds: a wider parent stays on screen as the ancestor of a sub-step inside the scope, Info rides along with what is kept, and the selected node is exempt. The rule is in `src-tauri/src/filters/` and the frontend's evaluator alike, held together by the shared corpus, so an agent's filtered read answers it the same way (see [*MCP server*](mcp-server.md)).
- **Archived and Backlog pills** — in the switch block of every view's Filter menu (before 2026-09-26 they sat behind a collapsed "Advanced" disclosure, in the Mindmap only; the List View reads the same shared filter and honours both, subtree gates included). An **Archived** pill that cycles **Inactive → Include → Exclude → Inactive** on click, overriding the status preset's own handling of anything whose *effective* Archival is **Archived** (an explicitly-Archived Goal/Project, or any scoped Task/Goal whose Resolution is **Completed** or **Missed** — the states that render the status row's archive-box badge) independently of achieved/frozen, which stay governed by the preset alone. **Inactive** (default, "as the preset says") defers to whatever the active preset already does (Plan/Start hide Archival-Archived items; All shows them). **Include** force-shows archived items even under Plan/Start. **Exclude** force-hides them even under All, hard-hiding the whole subtree so an archived item isn't kept visible merely as the ancestor of an unrelated, ordinarily-visible sibling. The pill reads the same way under **every** preset, **Do** included — it is one rule about archived items, not a per-preset carve-out — so under Do an effectively-Archived in-progress Task is hidden by **Exclude**, and an archived Commitment is force-shown by **Include**. Beside it sits a **Backlog** pill with the same three modes and the same relationship to the preset, governing Tasks in the **Backlog** (see [*Tasks*](resources.md)): **Inactive** defers (Plan/Start hide them with their subtrees; All and the Backlog preset show them), **Include** force-shows them under Plan/Start, and **Exclude** force-hides them even under All, subtree and all. The two pills are independent — a backlogged Task whose window has lapsed answers to both.

<a id="no-retyping"></a>**No retyping** (removed by the user on 2026-09-27). A node keeps the kind it was created as, and nothing changes it: there is no type cycle, no **Set type** entry in the node's context menu, and no backend command that moves a node from one table to another (`retype_node` and the flow-item `convert_flow_item` are gone with it). `Ctrl+↑` / `Ctrl+↓` are **unbound** — the Mindmap does nothing on them, and nothing else was given them. To make something of another kind, create it as that kind and move or delete the old node. Retyping had shipped as one atomic backend command that carried every field it could, named everything it would drop — a status or Verdict with no counterpart, a Time Scope, Plan, Backlog, Agentic or Asynchronous flag, tags, block reasons, dependency edges, children the new kind could not hold — in a confirmation prompt, climbed to the nearest acceptable ancestor when the new kind could not hang where the old one did, and asked for a window when a node became a Commitment with none in reach; all of that went with it.

**Copy+Paste duplication:** pasting a **Cut** selection moves it. Pasting a **Copy** deep-clones the
whole selected subtree onto the target instead, leaving the original exactly where it was — copy and
cut then differ only in whether the original survives, which is what the two gestures mean
everywhere else. It is deep by default, with no prompt: the copy is a real, independent subtree, and
editing one side never changes the other. The duplicate **keeps the original's title** (no
`" (copy)"` suffix) and carries everything the original holds — status, tags, notes, Time Scope,
on-exit behaviour, Plan, delegate, block reasons, privacy, position, its **beads id** (see *Beads
id*), and its dependencies. Those dependencies point at the **same targets** the original's did, even
when a target was itself inside the copied subtree: copying a subtree whose members depend on each
other produces a copy whose members still wait on the originals. (That mirrors a plain reparent and
is the conservative reading; Flow instances solve the same problem by remapping per instance, and
that is the model to reach for if this proves wrong.)

Projects, Domains, Tags, Goals, Tasks, Infos, **Flows and flow items** are duplicable. Aspects,
Commitments and Habit occurrences are not, and a Flow hanging under a copied node is still not
copied with it — but it is now **named**, not dropped in silence (see *A Flow left behind*, below).
A paste whose selection includes any of these pastes the rest and says in a toast what
it skipped — **grouped by reason, one sentence per reason**, because only one of the reasons is about
the destination. An Aspect is fixed wherever you point it, a Habit repetition has no row behind it to
copy, and a Commitment or a flow item leaving its own Flow has no duplicate at all though cut still
moves it; telling the user any of these "couldn't be pasted here" sends them to change a destination
that was never the problem. A mixed selection reports every reason it hit, in **one** toast: the view
holds a single pending toast, so a second would overwrite the first and skip a node in silence. A
toast stays up long enough to be read, which is a function of how much it says, not a fixed three
seconds. A paste the **backend** refuses says so too, naming the reason it gave rather than leaving
a board that silently did not change; when the same paste had also skipped something, the two are
shown together (see *When a gesture cannot act*). And the **destination** is checked as a node
before anything on the clipboard is considered: a folded run of Habit history or a virtual
occurrence refuses every paste for one reason, said once, rather than telling the user of each
node in turn that it cannot sit under a Task.

**A Flow left behind.** Every other skip is about a node that was put on the clipboard. This one is
not: a Flow hanging *underneath* a copied node is never copied with it — the duplication walk does
not descend into a Flow — so the pasted subtree comes out smaller than the one that was copied, and
nothing in the selection hints at what went missing. It is reported as one more reason in the same
composed toast, and it is the one reason that **names** rather than counts: the other skips are
about nodes the user selected and can still see, where a count identifies them, while a left-behind
Flow was never selected and is invisible in the paste, so "2 Flows weren't copied" would leave the
user hunting the copy for whatever is absent. The names are the remedy — they are what you go and
copy across on their own. Past **three** names the sentence counts the rest ("and 4 more"), because
a toast is a viewport strip and a Domain that has collected a year of Habits would fill it with a
list nobody reads. The report changes nothing about what gets copied: everything that can be is,
and this only says what the copy could not carry. A **cut** says nothing, because it loses nothing —
a move re-points one parent link and the whole subtree follows, Flows included.

The refusal that **is** about the destination names the kind it refused, what that kind was dropped
on, and — read off the drop-target rule itself, never off a list kept beside it — every kind that
*would* have taken it: "1 Goal can't sit under Task — only under Aspect, Domain, Project, Goal." It
is counted **per kind**, so a Goal and a Project refused by the same Task get a sentence each; one
count over both would state a rule true of neither. A flow item is told about its Flow instead of
being given that list, because a flow item's legal parents carry the same labels real nodes do and
the list would read as a claim about Tasks and Goals in general.

Otherwise a copy is refused exactly where a move would be, by the same
drop-target rule; it lands at the end of the target's children; it is atomic, so a failure part-way
leaves the tree untouched rather than half a subtree; and it leaves the clipboard intact, so the same
subtree can be pasted into several places.

**Copying a Flow.** A Flow is usually built by copying the one next to it and changing the schedule
or the target, so the copy is a **complete** clone of the template *and* its Recurrence: the flow
row, its items, their Cycle Scope / Cycle Plan pairs, intra-flow dependencies remapped onto the
clone, the Repetition (Start anchor, Gap, end), the Consumption tree and privacy. **Copying a Habit
gives you a Habit**, recurring on the same schedule from the same anchor — the Start is deliberately
*not* moved to today, because the copy is about to be edited anyway and a rule that quietly re-dated
it would be the bigger surprise. A copy of a daily Habit started in July therefore renders every
iteration since July until it is given a schedule of its own; that is an accepted consequence, not an
oversight. Its **Target Node** is inherited exactly as stored: a Flow that never named one has a
derived target meaning "my parent", so the copy's instances land wherever the paste put it, while a
target chosen deliberately keeps pointing where it was put. Two things are left behind: **completion
history** (its occurrences' overlays belong to the original — the copy has not been done, and its
cycle pairs are new rows, which is what a completion is keyed on) and **started instances** (`flow_instances` and the
Goals and Tasks they materialised are real work standing somewhere on the board).

**Copying a flow item** is allowed **within the same template** — onto its flow or onto another item
inside it — and takes everything nested under it, its cycle pairs and its dependency edges, with an
edge between two copied items rewired onto the copies. Pasting one into a *different* flow is
refused: its Cycle Scope is an offset into its own flow's window, and another window does not share
it.

**Node identity.** A node's `id` is a **display key**: unique within the tree and comparable, and
nothing more. It is never parsed. The database row a node draws is a field of its own, `rowId`,
read through `rowIdOf(node)` — which **throws** on a node that draws no row (the synthetic root, a
folded run of Habit history, a wait's check task) rather than handing back a number that is
not one. Recovering the row by splitting the id on `-` and parsing the tail is how a virtual node's
`-virtual` suffix once became `NaN`, then `null` over IPC; the idiom is a lint error now.

Node ids are not stored: they are derived afresh on every tree build, and selection, collapse and
the subtree root survive a reload — and are persisted per tab — only because that derivation is
deterministic. So the existing spellings are **frozen exactly as written**: `domain-<id>` (for
every domain-table subtype), `goal-<id>`, `task-<id>`, `commitment-<id>`, `info-<id>`, `flow-<id>`,
`flowgoal-<id>`, `flowtask-<id>`, and the folded run's `habitrun-…` keys. A Habit occurrence is
spelled like any row of its kind, with its UUID for the id (`task-<uuid>`); the `habit-…` and
`habititem-…` keys it was drawn under before it was a row (ADR 0008) are gone. The one piece of
saved tab state that can name a node — its subtree root — is carried across: a root saved under an
occurrence's old key, or under the old minted key of a wait's check task, spawned wait or delegation
wait, is re-rooted at the node's key now, read off the `origin` the node carries; one whose node is
gone drops back to the true root, as any stale root does. Selection and collapse are not saved. Changing any other would silently orphan every tab's
saved state.

**A node kind added from now on mints a UUID** for its id instead of composing a string — which
makes decoding it impossible rather than merely discouraged. The UUID is a **version 5** UUID: the
SHA-1 name-based hash of the node's structural key under one fixed application namespace. It has to
be deterministic, not random, for the reason above — a fresh `randomUUID()` per build would lose
collapse state on every in-session reload, not just across restarts. It is undecodable, which is the
point; it is not an immutable handle — if a node's structural key changes, its id changes with it,
exactly as a composed id does today. The **Expectation** is the first kind to use it:
`src/utils/node-uuid.ts` holds the namespace constant and the minter, and mints the ids of a stored
Expectation (`expectation/<id>`), of a wait's open virtual check task (`expectation-check/<id>`), of a completed one
(`expectation-check/<id>/<due instant>`) and of a delegated Task's virtual wait (`delegation-wait/<task id>`). The two virtual ones draw no row, so
`rowIdOf` throws on them as it does on a Habit occurrence. The SHA-1 is computed synchronously in
`src/utils/uuid-v5.ts`, because the tree is built synchronously and `crypto.subtle` is not.
