# List View

*One area of the [Arlesh design specification](../../SPEC.md).*

A compact-card task list, reached via its tab in the top bar or the `Ctrl+L` shortcut (which names the List rather than toggling; the choice belongs to the tab and persists with it — see [Tabs](tabs.md)). Reuses the Mindmap's own loaded tree (flattened to Tasks) rather than fetching independently, so the two views never drift out of sync — a materialized Start-flow task or a virtual Habit instance shows consistently in both.

**Rows are Tasks** — stored, flow-materialized, and Habit occurrences alike, and a wait's virtual check task. Goals, Projects, Domains, and every other kind are never list rows — they appear in a row's **path header** instead (see below). **Commitments and Expectations are the exceptions:** a setting draws them either in their own **bands** *above* the task rows, or as **ordinary rows** among them (see *Commitments and Expectations* below). A row shows: a status control (click cycles To Do → In Progress → Done; disabled while the task is blocked, a Habit occurrence included), the title (click opens the Task editor; double-clicking anywhere else on the card opens it too, matching the Mindmap's double-click-to-edit gesture), the same status-icon badge row as the Mindmap node (scope/plan/flow/tag badges with tooltips), and the task's **tag pills** — clicking one inline adds it as a filter, per the general [Filtering Logic](filtering-logic.md). The card carries **no parent label**: the path header above the run already names the row's parent, so a label on the card only restated what was on screen a line above it. Tags stay, because a tag appears in no header and clicking one here is the only way to add it from the row. Each card spans the full row width, with generous padding for a sparse, readable list, and is washed in its aspect's colour (see *What a row's colour says* below). A Commitment or an Expectation row wears the same wash. Clicking anywhere on a card **selects** it (a highlighted border), for the keyboard bindings below.

**Commitments and Expectations.** Two kinds besides Tasks appear in the list, and one switch on the settings modal's List page (persisted app-wide) decides *where*: **in bands** (the default) or **as rows**. In band mode each kind gets a band across the top of the list, above the task rows — **Commitments** first, then **Expectations** — headed with its name and separated by a rule, taking no space at all when nothing matches. In rows mode they are merged back into the task rows at their own place in the tree, under the same path headers and indented the same way, so a Commitment reads where it hangs and a wait sits beside the work that depends on it. The switch covers both kinds together: a list mixing the two shapes would read as two lists.

The band differs from the rows **only in where a row sits, never in how it looks or works.** A Commitment row is a task row whose status control is the Commitment's own glyph: a click on it — like `Enter` — cycles the verdict **Unresolved → Kept → Broken → Unresolved**, `X` records Broken in one press, and a double click, a click on the title or `E` opens its editor. An unjudged Commitment is drawn like any other — its glyph already says Unresolved. *Superseded:* it used to carry a marked left edge, which read as a selection and said nothing the glyph did not (removed in Arlesh-637). An Expectation row's control is the wait's glyph, and a click on it — like `Enter` — releases the wait or takes the release back. A check task's row is a task row, and `Enter` or its status control completes the check. *Superseded:* the band used to draw two verdict controls, a tick and a cross, so that Kept and Broken looked equal; the user wants one consistent row control instead, so the band now uses the ordinary one (Arlesh-bzn). Both kinds are filtered by the preset in either mode — see the filtering paragraphs below.

**Keyboard interactions** (mirroring the Mindmap's bindings where they translate to a flat list):
- `Alt+F` — toggle the filter menu *(a [global binding](tabs.md) — declared once, not per view)*; `Alt+A` / `Alt+P` / `Alt+S` / `Alt+D` / `Alt+B` — jump to the **All / Plan / Start / Do / Backlog** status preset (matched by physical key), same as the Mindmap; `Alt+U` — select **Unblock**, which the Mindmap has no equivalent of and which sets the List View's own preset only, leaving the shared status preset where it was
- `Alt+E` — select the List View's own **Expectations** option: every pending, live wait and nothing else. Like Unblock it replaces the preset's rules for the list and leaves the shared status preset where it was
- `Alt+Shift+T` / `Alt+Shift+C` / `Alt+Shift+E` — show or hide **Tasks / Commitments / Expectations**, the [row-kind selector](#row-kinds)'s three toggles, by initial (matched by physical key). One modifier above the `Alt+letter` presets: those choose which *state* of row the list shows, these which *kind*. A refused toggle — the last kind still shown, or any kind while the Expectations option is chosen — changes nothing and says why in a toast
- `Shift+E` — create an Expectation under the selected row, through its editor (a wait is configured before it exists; the List View otherwise creates Tasks alone). `Shift+W` — on a selected Task, open its editor at the Expectation section with Asynchronous switched on, as on the Mindmap
- `Enter` — on an Expectation, release it or take the release back (a delegated Task's wait refuses out loud: only the Task being done releases it); on a check task's row, complete the check (the next falls due one interval later) or reopen the latest done one. No separate keys: `L` and `D` were removed by the user on 2026-09-24 as proxies for `Enter`
- `B` — put the selected Task in the Backlog, or take it out (acts on the selected row only)
- `W` — mark the selected Task **Asynchronous**, or unmark it ("wait"; acts on the selected row only, real Tasks only). A plain two-state toggle of the Task's own flag; unmarking drops its Expectation template — see [*Tasks*](resources.md)
- `↑` / `↓` — move the selection between rows (path headers are skipped); the commitments section is walked first and the task rows after, in the order the two are drawn; from nothing selected, `↓` selects the first row and `↑` the last. **The view follows the selection**: each row the selection lands on is scrolled into view with `nearest` alignment, so a row past the fold comes just far enough in to be read and a row already on screen does not jump
- `J` / `K` — scroll the list down / up **without moving the selection**, which stays where it is even once it has scrolled out of sight. A tap nudges the view by a fixed 24px — about one line of text and its leading, the unit a reader tracks, so the eye follows it without having to re-find its place — and **holding the key scrolls on continuously at 300px/s**, roughly four to five compact rows a second. The hold is driven by an animation frame loop rather than by key auto-repeat, so the pace is the app's rather than the machine's: the OS repeat rate is a per-user setting the app cannot see, and a fixed step per repeat came out several times too fast on a normal one. The loop starts after a short hold delay (so a tap stays a tap) and stops on the key's release, on the window losing focus, or on leaving the view. A fixed amount rather than a measured row height (the user's call): tapping moves by one predictable unit instead of lurching by whatever row is under the fold. Reading ahead and moving the selection are separate gestures; where they meet, the selection wins — scrolling away with `J` and then pressing `↓` re-anchors the view on the selection, because the selection moved and the view follows it. The corollary: `↓` on the last row moves nothing and so re-anchors nothing. **List View only** — the Mindmap already pans with the arrow keys when nothing is selected, and a canvas pans in two dimensions, so `J`/`K` there would be a narrower version of what is already available
- `Enter` — on a Task, cycle its status (disabled while it's blocked; on a check task it completes the check, and on a done one reopens it); on a **Commitment**, cycle its verdict: **Unresolved → Kept → Broken → Unresolved**; on an **Expectation**, release it or take the release back. A selection is one of the three, so they never collide. A commitment Habit's iteration is a Commitment row like any other and cycles the same way, its verdict written on it. It stays a key of its own now that Enter cycles: `X` reaches Broken in one press from any verdict, so recording a broken commitment never has to pass through saying you kept it
- `E` — open the selected row's editor (Task, Commitment or Expectation; a check task says it has no editor yet, a delegated Task's wait opens the Task's, and a Habit repetition says why it has none)
- `R` — rename the selected Task inline (Enter/blur commits, Escape cancels)
- `Ctrl+O` *(a [global binding](tabs.md) — declared once, not per view)* — search for a node by title, over **every** node kind (not just the Tasks the list shows), and **enter** the one you pick: the list re-roots at it and shows only the Tasks beneath it, with that root trimmed from the path headers and named in the top bar instead. This is subtree entry, not a filter — the filter chips, the status preset and the selection are all untouched, and the subtree composes with whatever filtering is already active. It does **not** replace the **Antecedent** pill and never did: entering a subtree *re-roots*, dropping everything outside the branch, where an Antecedent pill keeps the whole board on screen and narrows it, and carries Any/All/**Exclusion**, which subtree entry has no equivalent of. "Show me only what is under ARLESH" and "highlight the ARLESH work among everything else" are different questions, and only the first is subtree entry; "everything **except** what is under ARLESH" is only the pill's
- `Delete` — delete the selected row, after the same confirmation the Mindmap raises, and with the same cascade: the row's whole subtree goes with it, and the prompt says how much that is before you answer. One row at a time, since the list has one selection where the canvas has a multi-selection; nothing selected does nothing. Undone in one step by `Ctrl+Z`, like any other delete
- `Shift+Enter` — create a **sibling** of the selected row; `Tab` — create a **child** of it. The Mindmap's two creation chords, which mean something here only because the list is nested. Both read the parent off the selection, so both need a **Task** selected: a Commitment is not one (List View creates Tasks and nothing else), and with nothing selected there is no parent at all — that case is the path header's `+`. Holding either key creates one row, not one per repeat, and neither fires while an inline rename or a modal has the keyboard
- `Ctrl+O` *(a [global binding](tabs.md) — declared once, not per view)* — search for a node by title, over **every** node kind (not just the Tasks the list shows), and **enter** the one you pick: the list re-roots at it and shows only the Tasks beneath it, with that root trimmed from the path headers and named in the top bar instead. This is subtree entry, not a filter — the filter chips, the status preset and the selection are all untouched, and the subtree composes with whatever filtering is already active
- `Shift+Escape` — up one subtree level; `Ctrl+Escape` — straight back to the true root *(a [global binding](tabs.md) — declared once, not per view)*. Same semantics as the Mindmap's, and gated the same way (they do nothing at the true root, where bare `Escape` still deselects)
- `Escape` — deselect
- `Ctrl+Z` — undo the last thing you did to the board; `Ctrl+Shift+Z` (or `Ctrl+Y`) — redo it
- `Ctrl+M` — show the Mindmap, `Ctrl+P` the Plan View; `Ctrl+Shift+/` — open the keyboard cheat-sheet; `Ctrl+Q` — quit
- `F` with nothing selected — the board alone *(see [Tabs](tabs.md); `F11` is the global form)*

A shortcut requires exactly the modifiers listed — `Ctrl+E` does not open the editor, only a bare `E` does.

**Path headers** name where a run of rows lives. Contiguous rows sharing a location are grouped under one header spelling out their full chain — `Growth › CODE › ARLESH › Features` — rendered once above the run rather than repeated on every card; grouping falls out naturally from walking the tree in the same position-sorted order the Mindmap uses, so rows sharing a path already arrive contiguous and no separate sort/group pass is needed. A header names every ancestor **not** rendered as a row above the task: always through to the Goal (Goals, Projects, Domains and Aspects are never rows), plus any ancestor Task the active filter hides — so a subtask on screen without its parent still reads in context, at the cost of splitting a run per hidden parent. A run with no named ancestors gets no header rather than a blank one. A header carries **no kind glyph**: it opened with one for its nearest ancestor, behind a *Path icons* switch in the settings popover, and both are gone — a header is its titles, their separators and the `+`. The kind of the node a run hangs from is already said by the Mindmap, where the same `NodeIcon` vocabulary lives; here it competed with the titles it was meant to qualify and nobody read it. The header is visually lighter than a task card and stays on one line, and each segment answers three gestures, split on one line: **a plain click re-roots, a modifier click narrows.** A plain click **enters** that node as the subtree — the same shared re-rooting `Ctrl+O` performs, so the list shows only what is beneath it, the segment is trimmed from the headers and named in the top bar instead, and `Shift+Escape`/`Ctrl+Escape` are the ways back out; it is subtree entry, not a filter, and nothing about the chips or the status preset changes. **`Ctrl+click`** instead files the segment as an **Antecedent** pill, and **`Alt+click`** files it as one in **Exclusion** mode — the same pills the filter popover's combobox adds, on the element that already names the ancestors. Entering rebuilds the rows with that node as the frame, so everything outside the branch is never built; a pill leaves the flatten alone and filters the result, with a chip naming what is narrowing and the rest of the board one chip-click from returning. Same node, two different questions. Each gesture names an answer rather than toggling, so it is idempotent and the opposite gesture moves the pill across rather than adding a second one for the same node; `Ctrl+click` on a node already filtered *for* in **All** mode leaves that mode alone, since All and Any both keep the node in and only the chip chooses between them. `Alt+click` necessarily takes the run it heads off screen — that is what filtering a branch out means — so the chip is the way back, where subtree entry has the top bar's exit pills. The gestures are named in the segment's tooltip, since a modifier click nobody knows about is a feature nobody has. There is no keyboard equivalent of its own: a focused segment is activated with `Enter`, and `Ctrl+Enter`/`Alt+Enter` reach the two filter gestures only in so far as the browser carries the held modifiers into the activation click, which is what the UI Events spec asks for. The filter popover's combobox remains the keyboard-complete route to an Antecedent pill. There is no Goal-visibility toggle — the path always runs through to the Goal — and with the status preset already moved to the shared top bar, the List View has no toolbar of its own.
**Asynchronous first.** An **opt-in** grouping of the list, switched on from the settings modal's List page, **off by default** and persisted app-wide with the other display preferences. With it off, the list is exactly what the tree ordered and there is no section — manual ordering is untouched until it is asked for.

With it on, the list grows an **Asynchronous section at the very top**, above every path header, collecting the asynchronous work of the **whole filtered set** — every row whose Task is marked **Asynchronous** (see [*Tasks*](resources.md)), and everything hanging beneath one. The ordinary list follows below it with those rows taken out: a row is **moved, never duplicated**. Reordering within a run was the earlier shape and is gone — an asynchronous task only ever overtook its own siblings, so one marked deep in a subtree, with nothing asynchronous beside it, did not visibly move at all, which is exactly the case the setting exists for.

**Paths are drawn normally inside the section**, and so are the rows: it is an ordinary list with ordinary path headers, just a separate one. A lifted row **brings its subtree with it**, indentation intact and nothing left behind, because the indentation names a parent the reader expects to find above it; an asynchronous row nested inside another asynchronous row's subtree therefore rides up with the outer one rather than lifting twice. Each half is then **grouped by path independently**, which is what keeps both readable: a lifted row whose parent stayed behind gains that parent as a **header segment** instead of as indentation under a row that is no longer there, and the parent left behind keeps its remaining children correctly indented. One consequence is deliberate — the same path can head a run in **both** halves, named once per section.

The section **reads as a block**: the heading opens it and a **rule closes it**, drawn between its last row and the first ordinary path header. The commitments band gets its boundary from its wrapper's border, which is not available here — the section's rows are entries in the same flat list as everything below, and the keyboard walks that one order — so the rule is an entry in the list too, and it is drawn only when there is a list below it to be closed off from.

Both halves keep **pre-order** within themselves: this is a partition, not a sort, so nothing else about the order changes. With nothing asynchronous there is **no section heading at all**, not an empty one, and so no rule either; with everything asynchronous the ordinary list below is empty and draws **no stray header** and **no trailing rule** into empty space. Arrow keys run straight through — the commitments band, then the section, then the ordinary list — since the section is part of the same drawn order and not a separate keyboard world.

The **Mindmap is deliberately untouched**, in either direction. Sibling order there is set by hand with `Alt+↑`/`Alt+↓`, which is a deliberate and visible thing; silently rearranging a branch underneath it would overwrite an answer already given. Nothing here reorders anything stored: the setting affects the drawing of the list and nothing else.

**Creating tasks.** Three ways in, the same three the Mindmap offers now that the list is nested: `Shift+Enter` for a sibling of the selected row, `Tab` for a child of it, and a **`+`** at the end of each path header for a child of that header's last node — the one the run beneath it hangs from, so where the new row lands is exactly what the header already says. The `+` is the answer to "nothing selected means no parent", and it is drawn always rather than revealed on hover, since an affordance you have to hover to find is not a discoverable one; it is absent on a header whose chain ends somewhere a Task cannot live. **Tasks only** — no other kind is creatable from List View, and the Mindmap's `Ctrl+Enter` (insert a parent above) has no flat-list meaning. Creation goes through the same create command the Mindmap uses, and the tree reloads as it does after any create, so the new task is on the Mindmap immediately.

A sibling carries over the source Task's **own stored** Agentic flag, exactly as the Mindmap's `Shift+Enter` does (see [*Tasks*](resources.md)) — the same chord on the same Task cannot mean two things depending on which view you are in. A new task is created **To Do** and opens straight into the inline rename `R` already uses: **Enter** commits the title, **Escape** discards the task itself rather than just the edit, so a mistaken create costs nothing — and an empty title costs the same, since blank is not a name. A parent that could never hold a Task — a Habit repetition, which is derived rather than stored, or a kind the parenting rules refuse — **creates nothing and says why**, on the Mindmap's rule that an inert key is worse than a refusal.

**Deleting** is the same gesture as the Mindmap's and deliberately shares its parts rather than restating them: the same `Delete` chord, the same confirmation dialog (so the heading and the "this also deletes N descendants" line are one wording, not two), the same post-order subtree cascade, and the same writer — which is what keeps a single `Ctrl+Z` reversing a delete made from either view. A Commitment row deletes like any other, since it is a real node. A **Habit occurrence** deletes through the same confirmation, and its delete archives that one repetition: the Habit's template behind it is emphatically not what `Delete` on one occurrence should take away. A wait's check task, which draws no row, is refused out loud. Afterwards the selection steps to the **next row**, or to the one above when the deleted row was last, skipping anything that went with it — not the Mindmap's rule of falling back to the nearest surviving ancestor, because on a flat list a row's ancestors are usually Goals and Projects, which are never rows, so that rule would leave nothing selected most of the time.

The new row is **held visible while it stays selected**, which is the **focus exemption** (see [*Filtering Logic*](filtering-logic.md)) doing its ordinary job: creating a To Do task under the **Do** preset does not make it vanish mid-keystroke, and cycling its status while it is still selected does not eject it either. Move the selection off and it is filtered like any other row. Nothing is persisted and no filter rule knows about creation at all — the exemption is the selection, and the new row is simply what the selection has just become.

**Path headers** name where a run of rows lives. Contiguous rows sharing a location are grouped under one header spelling out their full chain — `Growth › CODE › ARLESH › Features` — rendered once above the run rather than repeated on every card; grouping falls out naturally from walking the tree in the same position-sorted order the Mindmap uses, so rows sharing a path already arrive contiguous and no separate sort/group pass is needed. A header names every ancestor **not** rendered as a row above the task: always through to the Goal (Goals, Projects, Domains and Aspects are never rows), plus any ancestor Task the active filter hides — so a subtask on screen without its parent still reads in context, at the cost of splitting a run per hidden parent. A run with no named ancestors gets no header rather than a blank one. A header carries **no kind glyph**: it opened with one for its nearest ancestor, behind a *Path icons* switch in the settings popover, and both are gone — a header is its titles, their separators and the `+`. The kind of the node a run hangs from is already said by the Mindmap, where the same `NodeIcon` vocabulary lives; here it competed with the titles it was meant to qualify and nobody read it. The header is visually lighter than a task card and stays on one line, and each segment is clickable: it **enters** that node as the subtree — the same shared re-rooting `Ctrl+O` performs, so the list shows only what is beneath it, the segment is trimmed from the headers and named in the top bar instead, and `Shift+Escape`/`Ctrl+Escape` are the ways back out. It is subtree entry, not a filter: nothing about the chips or the status preset changes. The chain closes with the `+` described above. There is no Goal-visibility toggle — the path always runs through to the Goal — and with the status preset already moved to the shared top bar, the List View has no toolbar of its own.

**Indentation** is the other half of the same rule. A row steps in once for every ancestor Task that *is* rendered as a row above it, so a task and its subtasks read as one piece of work rather than as unrelated items of the same size. Header and indentation partition a row's ancestors exactly — the header names every ancestor not on screen, the indentation counts every ancestor that is — so neither ever repeats the other and the list never leaves whitespace standing for a parent that is not there: under a filter that hides the parent (Do, typically) the subtask sits flush and its parent is named in the header instead. Depth is therefore *visible* depth, not tree depth, and is derived at render from the ancestors each row already carries — no ghost rows for hidden parents, which would mean the filter no longer removes what it says it removes. The step applies to the whole card, so the status control, badges and colour move together as one object; it follows the row title's own direction, so a Hebrew task indents from the right even in a left-to-right list; it is capped, so a deep chain cannot push titles off the edge; and it costs nothing at depth 0, so a list with nothing nested is exactly as wide as before.

**Filtering** shares the Mindmap's status preset, tag filters, and Info/Flow/Private toggles (same top-bar dropdown, same `FilterPopover`, same persisted state) — a filter set in one view is already applied when you switch to the other. That includes the Plan preset's **Plan scope**, set in the top bar beside the preset (see [*Mindmap*](mindmap-view.md)), which narrows the task rows the same way; the Unblock and Expectations options replace the preset's rules, so they ignore it and the top bar does not draw it while either is chosen. The **focus exemption** applies here too ([Filtering Logic](filtering-logic.md)): the selected row stays in the list, dimmed and in its own place, when your own edit stops it matching — it needs no ancestor chain, since a row's hidden ancestors are already named in its path header. It holds a row of **any kind** — a Task, a Commitment or a wait, in a band or among the rows — so marking the selected Commitment Kept under Plan, or releasing the selected wait under Expectations, leaves it on screen as completing a Task does. (It once held task rows only, and a selected Commitment vanished under your own edit.) The shared status-preset dropdown gains one further option while List View is active: **Unblock** — shows every blocked task, List-View-only, and does *not* change the shared status preset (switching back to the Mindmap shows whatever preset was last active there). Unblock *replaces* the preset's rules for the list rather than combining with them: the preset left in the shared filter is the Mindmap's, and the list reads it as All. It has to — Start hides a blocked task along with its subtree, which is exactly the set Unblock exists to show, so consulting it would empty the list in the one state the option is for. Everything that is not a preset rule still applies: tags, the Info/Flow/Private toggles, the Archived and Backlog pills, and List View's own pills. A seventh option works the same way: **Expectations** (`Alt+E`) — every pending, live wait, and no task or Commitment rows; it too leaves the shared preset where it was.

<a id="row-kinds"></a>**Row kinds.** The List View draws three kinds of actionable row — **Tasks**, **Commitments** and **Expectations** — and a selector at the top of the filter popover, above every other cluster and drawn only while List View is active, chooses which of them it draws: three toggles, all on by default. It is a filter on the kind of row, applied before and in addition to everything else, so a kind that is off is simply absent — its band or rows are not drawn — and a kind that is on still answers the preset and the pills as it always did. **At least one kind stays on:** a list showing no kind at all is an empty screen nobody asked for, so the last toggle still on is drawn disabled with a tooltip saying why, the store refuses the change, and its key says so in a toast. The selector stands aside while the **Expectations** option (`Alt+E`) is chosen, since that option already is a kind choice — waits and nothing else: every toggle is drawn disabled with a tooltip, its keys answer with a toast, and the stored selection is left untouched, to apply again once another option is chosen. Under **Unblock** and **Backlog**, which list Tasks only, it still applies — turning Tasks off there leaves the list empty, as asked. **Reset** turns all three back on. The selection is kept per tab with the rest of the List View filter; a tab stored before the selector existed, or a stored value that is malformed or names no kind, reads as all three. It is frontend only, like the List View's own pills: nothing reaches the board filter the backend or the MCP sees. Keys: `Alt+Shift+T` / `Alt+Shift+C` / `Alt+Shift+E`, named in each toggle's tooltip and in the cheat-sheet.

The commitments section consults only the dimensions a Commitment actually has — Antecedent, Scope and Verdict. A Commitment hangs off the same tree as everything else, so it has a full ancestor chain and answers an Antecedent pill exactly as a task row does: narrowing to a branch would be a lie if the band above the rows kept showing commitments from outside it. A Task-status or Blocked pill is not *failed* by a commitment, it simply does not apply to one, so asking to see in-progress tasks does not empty the band. **Unblock**, **Backlog** and the **Expectations** option show no Commitment, since none is a state a Commitment can be in. The band also answers the **subtree** rules the task rows answer: a Commitment whose ancestor is hidden as a whole subtree — a Frozen/Archived Project, a backlogged Task, or a Habit occurrence whose window has not opened (see [*Habits*](habits.md)) — goes with it, because a band that kept showing commitments from a branch the list has dropped would be describing a board nobody is looking at.

The **Expectations** consult the preset by the [Expectation rules](resources.md) — a pending, live wait under All and Plan, and under Start whether or not it has a Check every (only without one while the app-wide **Start hides waits that have checks** setting is on); released and archived ones under All only — together with the same subtree gates the task rows answer, and the **Antecedent** pill, the one pill dimension a wait has. **Unblock** shows none: a wait is never blocked. The **Expectations** option shows every pending, live wait, reading the hard-hide rules under the neutralised filter exactly as Unblock does, and no task or Commitment rows at all. A wait's check task is a task row and answers the ordinary Task rules.

On top of the shared filters, the List View adds its own filter dimensions — all in the same Any/All/Exclusion pill pattern as tags (a searchable combobox for entity-valued dimensions, fixed-option buttons for enum-valued ones), grouped into two extra clusters ("Hierarchy" and "Status & Scope") in the same `FilterPopover` while List View is active. Picking a candidate adds it and it appears as a chip in the top bar's active-filter row, exactly like a tag:

| Dimension | Values |
|---|---|
| Antecedent | Any node on the task's ancestor chain — Aspect, Domain, Project, Goal or Task — at any depth. Its combobox searches **every** node, the way `Ctrl+O` does, not only the ancestors of rows currently on screen: filtering to a branch nothing visible descends from is exactly the case the filter exists for. It is also added inline, without opening the popover, by `Ctrl+click`ing (include) or `Alt+click`ing (exclude) a segment of a row's path header — see *Path headers* above |
| Dependency | A specific Task/Goal this task depends on |
| Task status | To Do / In Progress / Done |
| Goal status | The resolved nearest-ancestor Goal's status |
| Project status | The resolved nearest-ancestor Project's status |
| Verdict | Unresolved / Kept / Broken — applies to the commitments section only |
| Scope | Unscoped / Active / Overdue / Lapsed / Planned / Unplanned — independent axes, so e.g. Unscoped + Planned can both apply to the same task |
| Blocked | Blocked / Not blocked |
| Agentic | Agentic / Not agentic — the flag as the task *reads* it, its own or inherited (see [*Tasks*](resources.md)). Independent of the delegated/undelegated question |
| Asynchronous | Asynchronous / Not asynchronous — the task's **own** flag (see [*Tasks*](resources.md)); it does not inherit, so a subtask of an asynchronous task reads as not asynchronous |

## What a row's colour says

A row is **washed in its aspect's colour**, the same wash a [Steps View](steps-view.md) card takes
and from the same shared stylesheet, so a Task reads as the same part of the board on either
surface. It is **flat**: a row's colour no longer fades with how deep its node sits. The fade dated
from when the List View was the only flat surface and a row's colour was the only thing saying where
it came from — the path header says that now, in words, and a depth ramp also meant the colour said
nothing consistent from one row to the next. The Mindmap and the drag ghost keep their depth-shaded
fill; this rule is the List View's, the Steps View's and the [Plan View](plan-view.md)'s.

It is a small share of the hue mixed into the row surface (`--surface-raised`), not the colour
itself, with the row's muted text derived from that surface. The contrast reasoning and the numbers
are the Steps View's (see *What the fill says* there). On a row the base is the raised surface rather
than the card background, so the margins are a little thinner: for the six seeded aspects the
primary text bottoms out at 8.28:1 in dark (Self) and 9.82:1 in light (Flow), the muted text at
4.53:1 and 5.03:1. Against the page a row stands at 1.34–1.59:1 in light (Self 1.19:1). Self and Flow
take the per-aspect strengths described there, so the two greys differ on a row as they do on a
card.

**The colour says nothing about state.** The status control's glyph draws done, in progress and
blocked (and is disabled while blocked); the badge row carries archived, frozen, backlogged, agentic
and asynchronous; a Commitment's status control shows its Verdict.
