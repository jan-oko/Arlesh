# Habits

*One area of the [Arlesh design specification](../../SPEC.md).*

A **Habit** is a Flow with a **Recurrence** pattern (a flow becomes a Habit when given a Recurrence — stored in a `flow_recurrences` row keyed by the flow, whose presence marks the flow as a Habit; a Habit requires a scoped flow). Its instances are generated automatically and are **virtual**: each is identified by `(instance, iteration scope, cycle pair)` — where an instance is a flow item **or the flow root itself** (the root materializes as a normal Task/Goal, so it is a first-class completable instance, not merely an aggregate of its items; an item-less habit therefore still has one instance, its root) — and rendered from the template, with only divergences persisted — status, an occurrence's own title, block reason and Plan, and a deletion tombstone as **Modification** rows, and each iteration's dependency changes beside them (see *Editing one occurrence*). The **cycle pair** is part of that key because a flow item with N pairs draws N instances in a single iteration, exactly as it materializes N items when the flow is started: a morning and an evening occurrence of the same item are two things to complete on the same day, and ticking one must not tick the other. The root, and any item with no pairs, key on the `0` sentinel. The root instance's title reads `{flow title} {start scope}` (e.g. "Exercise W22").

**Recurrence** = **Repetition** + **Consumption**:

- **Repetition** — a Start anchor, an optional **Gap** of N of a scope kind ≥ the habit scope (default: no gap, continuous), and an optional end.
- **Consumption** (per-habit, user-configurable tree):
  1. **Destructive** (unfinished instances lapse when their iteration passes; bounded) vs **Accumulating** (they survive).
  2. If Accumulating: **Overlapping** (new iterations generated regardless) vs **Blocking** (withheld while unresolved instances exist).
  3. If Blocking, the **catch-up policy** when the open iteration completes: *all pending* (every missed iteration, in order), *next* (advance by one), or *latest* (jump to current; the skipped iterations derive as **Missed** — see *Generation* below, nothing is stored for them).

**Generation.** Iterations are **derived**, never persisted per iteration: a pure function of the Recurrence, the reference day, and the completed iterations (the only persisted facts — a completed instance carries a `resolved_at`). Each started iteration is classified `Active` / `Done` / `Lapsed` (Destructive, passed unfinished) / `Missed` (a Blocking `latest` skip). Only iterations whose window has begun are generated; future ones are not drawn (a node standing in for them is `Arlesh-9md`). A day-and-up window begins and ends at 02:00 (see [*The day boundary*](time-scopes.md)), so a daily Habit turns over then and not at midnight: at 01:30 yesterday's iteration is still the open one. An iteration is *resolved* when every one of its (non-tombstoned) instances is done. Consumption semantics: Destructive lapses any past unfinished iteration and keeps only the current window active; Overlapping keeps every started iteration active until done; Blocking withholds beyond the open iteration and, on completion, advances by **next** (release the next), **latest** (jump to the iteration containing the completion day; skipped ones become Missed), or **all pending** (release the whole backlog up to the completion day as active, blocking again beyond it). **Each instance carries its own window.** A flow item's Cycle Scope resolves against *that iteration's* window start — backend-side, through the same offset arithmetic `start` uses, so a rendered occurrence and a started one cannot disagree about when "the 2nd day of week 3" falls — and the instance's Timing is read from it rather than from the iteration's. A Morning item inside a day-long iteration is Active during the morning and, under Destructive, Lapsed from noon; a Tuesday item inside a week-long one is Active on Tuesday alone. Sub-day windows obey **Consumption** like every other size: an Accumulating habit's passed occurrence piles up rather than lapsing, and if a morning routine should vanish at noon, Destructive is what says so. An occurrence whose window has not opened is **Pending**, and whether it renders is the **status preset's** decision, not generation's: **All shows it** — All's contract is that it shows everything, and a Habit's later-today items are exactly what one looks at All to see — while **every other preset hides it** (**Plan**, **Start**, **Do** and **Backlog** alike), together with its own subtree, so this evening's item does not sit among the morning's work (children nest under their parent's first occurrence and would otherwise be redrawn a level up). Backlog is no exception: an unopened window is not work that was set aside, and the preset that exists to show what you put down has nothing to say about what has not started. The subtree rule holds on every surface it is drawn on — the Mindmap prunes it, the List View's task rows walk their ancestors for it, and so does the **Commitments band** above them, so a Commitment hung on an unopened occurrence never outlives the occurrence it belongs to. The occurrence is generated and sent either way; dropping it backend-side put it beyond every preset at once. The rule is scoped to the occurrences a Habit generates in bulk: a hand-made task scheduled for next week is Pending too and still plans, as it always has. (Exact-time `HH:MM–HH:MM` cycles stay deferred with the cycle editor that would enter them.) A Destructive iteration's virtual instances (root and items alike) map onto the Task/Goal Archival model in [*On-exit behavior*](time-scopes.md) once their window has passed — a past-window instance is *effectively archived* regardless of whether it's `Done` or `Lapsed`, so a habit occurrence with some items completed and others missed still archives as a unit, rather than partially lingering visible via its completed siblings.

**Display.** Instances render under the Target Node — the Flow's own when it has one, otherwise its parent (and, only if that parent is not in the rendered tree, the Flow node itself). Active and past instances render directly; future instances are not drawn. (A node standing in for them, and pinning one out of it, is tracked as `Arlesh-9md`.)

**Collapsed history.** At the other end of the same timeline, a **collapsed node** stands in for a run of **passed** iterations — those whose window has closed, which the backend states per iteration as its exclusive `window_end` rather than leaving the renderer to redo the Repetition's offset arithmetic. *Every* passed iteration folds, however it ended: Done as much as Lapsed, Missed and Expired, because the pile-up is the problem and a kept daily habit accumulates fastest of all — three hundred and sixty-five nodes a year. The iteration whose window is still open always renders on its own, and Destructive needs no rule of its own here: its Lapsed iterations fold the moment the next window begins. The node reads its Habit's title and then its tally — "Journal: 14 passed · 9 done, 5 missed", where *done* means finished as intended, which for a commitment Habit is **Kept** — and names its day span in a tooltip. The title is on the node because a run stands among the Habit's own live iterations and, under a busy target, among other Habits' runs: a tally alone says what happened but not to what. The **threshold** is a setting ("Collapse habit history after N", default 3, minimum 2) in the Mindmap's gear popover; it applies to every Habit and is an app-wide preference, not a per-tab one. A run shorter than it draws its iterations directly.

`Ctrl+/` — the binding that collapses any other node — **expands** a collapsed run, and the expansion **persists with the tab** (an ordinary collapsed node does not: forgetting a collapse merely shows something again, where forgetting an expansion would silently re-fold what the user opened). The expansion is a **scope-levelled tree**, not a flat list: walking up from the iteration's own scope kind through day → week → month → season, a level is inserted for a kind only where the run spans **more than one** of that unit — five days inside one week give five day nodes and no week level, three weeks inside one month give a week level and no month level. **Year is a display-only grouping above Season**, keyed on the year a Season is labelled with so a Winter straddling New Year stays one node: nothing else changes, and there is no Year scope row, no Year in the picker and no Year-scoped items. Each intermediate level node carries its own tally ("September · 18 done, 12 missed") — its Habit is already named by the run above it — and **comes up collapsed in its turn**: opening a run is a request for the shape of the history, not for every day of it, so a year opens as four seasons rather than as three hundred and sixty-five nodes. Every level therefore answers to the same inverted set the run does — a habit-group node is drawn shut unless the user has opened it — rather than to `collapsedNodeIds`, whose absent-means-expanded reading is the wrong way round for anything the fold draws. Each opens independently with the same gesture.

`Ctrl+Alt+/` is the way past that one level at a time when the days themselves are what you want: it expands the selected node **and everything beneath it**, so a run opens with all its levels and all its iterations at once. It is one walk of the *drawn* tree rather than the loaded one — the fold's nodes have no counterpart in the loaded tree — and it needs no second pass, because a run's levels and iterations are built the moment the fold builds the run and are merely drawn shut. Going down, it writes to whichever set each node answers to: it clears ordinary nodes from `collapsedNodeIds` and adds the fold's nodes to the opened set. Each kind therefore keeps the persistence rule it already had — the fold's openings are written down with the tab, the ordinary expansions are not — rather than acquiring a third.

The same chord **shuts** a subtree again, and the mirror runs through both sets in reverse: ordinary nodes are added to `collapsedNodeIds`, the fold's nodes are removed from the opened set. Which way a press goes is decided by the node it was pressed on, and by that node alone — **drawn shut means open it, drawn open means shut it** — read off the single reconciled set the layout uses, so neither polarity is re-derived and a subtree that is a mixture of open and shut (which it usually is) cannot leave the gesture undecided. The pressed node's own state is what changes, so a second press is always the other direction. A collapse descends past that node rather than merely shutting it, because the two sets are also what `Ctrl+/` reads: leaving a run's levels open would make the next single-node press reveal every iteration instead of the levels. The consequence for what is written down is that a recursive collapse takes every group id in the subtree back out of the opened set, so opening and shutting a run leaves nothing persisted behind it.

A collapsed node is **selectable but not filterable**: arrow keys land on it and leave it — onto it from its neighbours, off it to them, and in and out of its scope levels — and it is otherwise a display node with no row, no status, no scope and no tags of its own — so the fold runs **after** the filter rather than before it, over whichever iterations the filter kept. It therefore renders exactly when at least one iteration behind it would have. Because it exists only in the tree the canvas draws and has no counterpart in the loaded one, **directional movement reads its candidates off the drawn tree**: a node the fold invented has no relatives in the loaded tree, and one the filter dropped is not a relative in the drawn one. Nothing new is persisted about iterations either: they stay derived, and the only stored state this adds is the threshold and which group nodes — runs and scope levels alike — are open.

**Added children.** A virtual instance can be given **real children of its own**, attached to that occurrence and to no other. The instance stays virtual — nothing materialises on first touch (ADR 0002) — and the children are ordinary rows keyed to the occurrence by the same `(item_type, item_id, iteration_scope_id, cycle_id)` quadruple a Modification is, so storage stays proportional to divergences rather than to iterations. They are created with the same gesture used everywhere else, in any kind **a Task can parent** — Task, Goal, Commitment, Info — and are fully editable nodes: scopeable, taggable, plannable, completable, and able to hold children of their own in the ordinary way (only the first level is attached; everything below it is an ordinary parent link). Because a virtual instance has no row id, an added child's own `parent_type`/`parent_id` name the occurrence's **host** — the Target Node the occurrence renders under — while the attachment is what makes the occurrence its parent: containment, inheritance and Archival all follow the occurrence, and a child whose attachment were ever lost would surface beside the occurrence rather than nowhere. **Containment** applies normally: the child's Time Scope must sit within the occurrence's window (an occurrence's own, resolved Cycle Scope when a pair drew it, else the iteration's), and its Plan within its Time Scope. The occurrence's window is settled when the child is attached rather than re-derived on every read, because resolving a Flow Window mints scope rows and the ancestry climb that enforces containment is a read. A **Commitment** child is the one kind written already carrying that window as its own, because a Commitment with no effective window has nothing it could ever be kept or broken over; the other three are written unscoped and inherit it. A Commitment is configured before it exists — `Shift+C` opens the editor first — so its verdict, Verdict Window, privacy and tags are written onto the attached row before the board redraws, and it appears once, configured, rather than twice. Leaving the editor's window empty keeps the occurrence's; naming one narrows it, and a window the occurrence cannot hold is refused in the editor with nothing left behind.

**Iteration resolution is unchanged**: an iteration resolves when every one of its *template-derived instances* is done, and added children are not instances. Nothing hung on an occurrence can withhold the Habit's next occurrence under Blocking Consumption. What guards completion instead is a **prompt, with nothing stored**: marking an occurrence `done` while it still holds unfinished children is refused pending confirmation, and the refusal **names them** — a confirmation that can only be accepted blind is not consent. Confirming marks the occurrence done and leaves the children in place; declining writes nothing. A Task is unfinished until `done`, a Goal until achieved or archived, a Commitment until a verdict is recorded (kept **or** broken — either is an answer given), and an **Info is never unfinished**: a note is not work. The guard watches `done` alone; a commitment Habit's iteration is kept or broken, and a verdict is not a claim that anything under it was finished. Rejected: a per-child counts-toward-completion flag — it puts a permanent setting on every child to express something that matters at exactly one moment, and default-on it let a jotted note stall a habit indefinitely.

**Archival as a unit.** Added children take the occurrence's effective Archival with it: the occurrence's window governs them, on-exit **Archive**, so when the window passes they archive together rather than lingering beside a closed occurrence. Nothing is deleted and All still reaches them. An added child makes its occurrence **divergent**, so editing the Habit's scope or repetition raises the existing *archive-and-new vs delete-and-regenerate* prompt; delete-and-regenerate removes added children along with the instances they hung off, which is what the prompt exists to warn about. Retyping an added child keeps it on its occurrence. Deleting one never touches the template.

**Editing one occurrence.** A virtual occurrence of one of a Habit's **items** can be edited on its own, in the fields the Modification row was designed to hold: its **title**, its **block reason**, its **Plan**, what it **waits on** in its iteration, and **deleting it** from its iteration alone — beside its status, which its own status control already writes. The instance stays virtual (ADR 0002). Every field is a **divergence** from the template: setting it back to what the template says clears it rather than recording a copy — typing the item's own title back, emptying the block reason, choosing *Follow the Cycle Plan*, ticking exactly the template's dependencies — and a row is deleted once nothing in it diverges any more, so storage stays proportional to the occurrences that actually differ. Changing every occurrence is what editing the template is for, and nothing here writes to it or asks about the others.

It is edited in its **own editor**, opened by double-clicking the occurrence on the Mindmap or in the List View — not in the Task editor with fields hidden. Most of a Task's editor is about a row that exists — tags, Time Scope, on-exit behaviour, Backlog, Agentic, Asynchronous, privacy, the `bd` link — and an occurrence has none of those of its own, so the Task editor would have hidden more than it showed; and its dependency picker offers real Tasks and Goals, where an occurrence waits only on another item of its own Habit. The occurrence editor shows what applies: title (the template's shown as the placeholder), block reason, and for a **task** occurrence the Plan and the dependencies; a **goal** occurrence has neither, as a goal has no Plan and never waits. A save is **one Gesture** however many fields it changes, so one Ctrl+Z takes the whole edit back, and a refusal part-way takes back what it had already written. The **iteration root** is not edited on its own: its title is derived from the iteration, and deleting it would be deleting the iteration.

- **Title.** The occurrence reads its own title wherever it is drawn; the next iteration reads the item's.
- **Block reason.** One reason, in the row's single `blocked_reason` column — the overlay's shape, where a Task's reasons are an ordered list. An occurrence with one reads **blocked** exactly as a Task does (the red stop-sign; the presets that hide blocked work hide it). A flow item has no block reason of its own, so there is nothing to inherit.
- **Plan.** A **true three-state**: *inherit* the Cycle Plan (the default), *planned* into a window of its own, or *deliberately unplanned*. The last is not the same as the first — an occurrence whose Cycle Plan was taken away must not quietly get it back — which is why the row carries a `plan_overridden` flag beside the window's `plan_start_id`/`plan_end_id` rather than reading NULL as "inherit" the way its other columns do; a sentinel scope id would put a magic number in a foreign key. The window is a start/end pair, as a Task's Plan and a Cycle Plan both are, picked with the **same Plan field** a Task's editor uses, and its Clear means *unplanned*. **Containment** holds as everywhere: the window must sit inside the occurrence's own resolved window — its pair's Cycle Scope within that iteration, else the iteration's — and is refused at write time otherwise. Only a **task** occurrence has one.
- **Dependencies.** Template dependencies now **block occurrences** the way a started flow's do: an occurrence waits, in its own iteration, on every occurrence of each item its template says it depends on — fan-in, as in [*Flows*](flows.md) — and reads blocked, `Blocked by {title}`, while **any** of them is unfinished (a task not done, a goal not achieved). A **deleted** occurrence holds nothing up. An iteration can **add** an edge or **remove** a template edge for itself; they live in `habit_instance_dependencies`, keyed by iteration and **item**, not by occurrence — the table has no cycle-pair column — so an edit applies to every occurrence of that item in that iteration, exactly as a template edge does. The editor sends the whole set the occurrence should wait on and the backend records only the difference from the template, so ticking the template's set again leaves no rows. Only a task waits, a blocker is another item of the same Habit, and a set that would make the iteration's graph **circular** is refused, as a circular dependency is refused everywhere.
- **Deleting one occurrence.** `Delete` on an item occurrence — or the editor's *Delete this occurrence only* — writes a **tombstone** (`deleted`) instead of refusing. It is the conservative reading of a delete: nothing is removed from the template or from any other iteration, the occurrence **no longer counts towards its iteration's resolution** (the iteration resolves once every instance still in it is done, and closing the iteration does not write the deleted one back), and it holds up nothing that waits on it. It is **not** dropped from the payload: it is drawn **archived** — so every preset but **All**, and the archived filter set to exclude, hides it — with its archive badge saying it was deleted from this iteration. It comes back two ways: Ctrl+Z, and the editor's *Restore this occurrence*, reached from All. A delete that would take something with it is **refused, by name**: an occurrence still holding an added child, or the occurrence its template child items nest under (the item's first), which holds their occurrences — delete those first. A selection of occurrences deletes as one undo step; an iteration root in it refuses it, and a selection mixing occurrences with real nodes is refused whole, as a destructive gesture never acts on half of what was selected.

**How an edited occurrence reads.** Its own fields show themselves: the title it was given, the stop-sign of its block reason or of an unmet dependency, the archive badge of a deleted one. Only the **Plan** carries a mark of its own, because an occurrence's plan is otherwise indistinguishable from its Cycle Plan: the calendar badge is drawn in the accent colour, with a tooltip saying the plan is this occurrence's own, and a deliberately unplanned occurrence keeps a **struck-through** badge so it cannot be mistaken for one never touched. A **display-pinned future** occurrence can be edited too; its overlay is keyed by its iteration scope like any other and is waiting when the iteration arrives. The effective values are what the MCP snapshot's iterations report.

**Divergence and the template.** Every one of these is a **divergence**: it survives the Habit being archived, it raises the *archive-and-new vs delete-and-regenerate* prompt when the Habit's scope or repetition is edited, and delete-and-regenerate clears it — the per-iteration dependency changes included. Un-completing an occurrence, or its iteration, clears only its status and leaves every other field in place.

**Editing an item's cycle pairs keeps its occurrences.** A pair's id is part of every occurrence's identity, so the item editor's save **diffs** the pairs rather than replacing them: a pair whose Cycle Scope is still asked for keeps its row — updated in place when only its Cycle Plan or its position changed — and only pairs that really came or went are inserted or deleted. A save that leaves the pairs alone, a title-only one included, writes nothing to them. A pair is matched by its **Cycle Scope** and not by its Plan: moving a pair to another part of the day is a different occurrence, since a title or a Plan recorded against the old window would not belong to the new one. When a change would still leave recorded edits behind — a removed pair's occurrences, or the no-pair occurrence of an item given its first pair, holding a status, an own title, block reason, Plan or tombstone, or an added child — the save stops and asks **the Habit editor's own question**, with the same two answers: **Archive & new** lands the whole save on a fork of the Habit (the template with no history, carrying the Recurrence and privacy the item editor does not restate), and **archives the original** exactly as the Habit editor's does — it stops recurring after today, keeping its pairs and everything recorded on them; **Discard & regenerate** clears the Habit's recorded edits, exactly as the Habit editor's does, and saves. Dependency changes are keyed by item and are not orphaned by a pair edit. The save is one Gesture, question or no question: the refused attempt wrote nothing, and the answered one is one undo step.

**Commitment habits.** An iteration of a Habit whose Instance Type is `commitment` renders as a **Commitment**, not as a Task or a Goal: the commitment glyph, the Verdict badge, and the two verdict controls in List View's commitments section — never a status control to cycle. It is selectable on the Mindmap like any other node, where `Enter` cycles its verdict and `X` records Broken, exactly as on a real Commitment; the tick and the cross remain List-View-only controls. That iteration's Verdict is its **Modification** row, in the same `status` slot an ordinary instance keeps a task status in; clearing it back to Unresolved removes the row, exactly as un-completing a task instance does. Nothing translates between the two vocabularies: a stale `done` is not read as `kept`. The items beneath the iteration are the flow's **task** items, rendered as Tasks — the supporting steps a Commitment legally parents — and, per [*Commitments*](resources.md), none of them ever gates the verdict. A commitment flow whose template holds a **flow goal** has no valid materialisation at all, since a Commitment holds no Goals: `start` is refused by `goals.parent_type`, and a Habit derives **no iterations** rather than drawing a subtree the model forbids — the Mindmap's load-condition banner names every flow it withheld, so nothing goes missing quietly. One consequence of a virtual iteration having no Commitment row of its own: its Archival is derived here rather than by the lifecycle — past **and** judged is settled and archives; past and unjudged stays live, because the answer is still owed, and is never **Missed**. What ends "still owed" is the **Verdict Window**, which the Habit carries on the flow row (see *Recurrence* above) and every one of its iterations resolves to: the backend derives such an iteration as **Expired**, and it archives still unresolved. Expiry is checked before the past-and-unjudged rule, because under the Accumulating + Overlapping Consumption a commitment Habit is fixed to, an unanswered iteration classifies Active rather than Lapsed right up until it expires. A Habit with no Verdict Window set keeps its iterations answerable indefinitely, exactly as a Commitment with none anywhere above it does.

**Editing** a Habit's scope or repetition prompts (**Archive & new** — archive the old habit and create a new one — vs *delete instances and regenerate*) **only when divergent instances exist**; otherwise it silently regenerates. **Archive & new** clones the template onto a new flow, which takes the edit, and **archives the original**: it stops recurring after the Day the edit is made on (by the 02:00 boundary), so every iteration that had begun keeps its history and nothing later is generated. The clone, the archive and the edit are **one Gesture** — a single `Ctrl+Z` takes back all three, and a refusal part-way leaves none of them behind. (Archiving a Habit on its own, outside this prompt, is `Arlesh-9md`.)
