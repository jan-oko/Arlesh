# Flows

*One area of the [Arlesh design specification](../../SPEC.md).*

A **Flow** is a template for a Goal/Task subtree, materialized on demand (e.g. an "Add Feature" flow of Specify → Implement → QA). It is a new node kind, created via a dedicated mindmap action, and may be parented under an Aspect, Domain, Project, or Goal.

A Flow has a title, an **Instance Type** (goal, task or commitment — what its root materializes as), a **Target Node** (where instances are created — **optional**: unset means the Flow's own parent, derived on read rather than stored, so a move carries the instances along, while a stored target is a deliberate override a move leaves alone), and a **Flow Window**. The Flow Window is either a **Span** — a coarse Duration of N of `day`/`week`/`month`/`season` (a relative length, snapshotted against the start anchor) — or a sub-day **Phase** — a fixed time-of-day carried date-free on the template: a part-of-day band (e.g. Evening) or an exact `HH:MM–HH:MM` range. Starting supplies only a date; a Phase window is combined with that date via the part/exact scope constructors. A Habit with a Phase window recurs at the fixed time-of-day, stepping whole days by its Gap. A **task-instance** flow may also carry a **root Cycle Plan** — a relative plan window inside the flow window (like a flow item's Cycle Plan) — resolved into the root Task's Plan on start; goal-instance flows have none (Plan is task-only).

**Flow items** — a Flow's children are flow tasks, goals, Commitments and waits: ordinary Tasks, Goals, Commitments and Expectations plus one or more **(Cycle Scope, Cycle Plan)** pairs. A Cycle Scope is relative — the Nth subscope of the flow scope (null = the whole flow scope); a Cycle Plan is a relative Plan within it. A Task item may declare dependencies on **any other Task, Goal or wait item in the same flow**; nothing waits on a Commitment item, as nothing waits on a Commitment.

A flow item is a **Task**, a **Goal**, a **Commitment** or a **wait** (`flow_tasks`, `flow_goals`, `flow_commitments`, `flow_expectations`; the last two since migration 0094, Task b66). It is created under a flow (or another item) with the create chords, which inside a template make flow items, **inline** like any other: `Tab` and `Shift+T` a Task item, `Shift+G` a Goal item, `Shift+C` a Commitment item and `Shift+E` a wait item; `E` then opens its editor (see [*Keyboard interactions*](mindmap-view.md)). Where each may sit is the **parenting table stored nodes obey**, with no template-only exception (ruled by the user, 2026-10-03: "follow the table"), the Flow standing for its root: a Goal item under the Flow or a Goal item; a Task, Commitment or wait item under the Flow or a Goal, Task or Commitment item; a wait item holds nothing in a template, since a template holds no notes. A commitment Flow takes no Goal item, since its root is a Commitment and a Commitment cannot hold a Goal. The gestures that name no kind keep the older default — a flow root spawns items of its Instance Type, a flow item spawns items of its own kind — so a sibling made with `Shift+Enter` matches its parent's default. It is edited in a dedicated modal: title, cycle pairs, dependencies and privacy, and the fields its kind's occurrences read (see [Templates](virtual-nodes.md#templates)) — for a Task item among them a **Compound** switch, beside Asynchronous, and under the **Asynchronous** switch the same wait-template fields the Task editor shows (Task 611; the user, 2026-10-01: "add compound and async expectations to the template editor"). The Flow editor offers the same two for the root of a task-instance flow (ruled by the user, 2026-10-02: "iteration roots must also support compound and asynchronous"); a Goal item, and a goal- or commitment-instance root, have neither (a flow item has no status or block reason of its own — migrations `0011`/`0012` dropped both). A flow item keeps the kind it was created as — it cannot be converted between goal and task (see [*No retyping*](mindmap-view.md#no-retyping)). Cycle pairs are stored **relatively**: the Cycle Scope as a `(subkind, index)` (the index-th subkind unit within the flow window; null = whole scope) and the Cycle Plan as a `(subkind, start..end)` range within the cycle scope (null = no plan). A Cycle Plan's subkind is finer than its Cycle Scope's, or **equal** to it — the range is then `1..1` and the plan is the Cycle Scope itself. The editor sets only the equal form, for now: each pair's row in the Cycles list carries a plain **Planned** toggle (off by default; pressed when on), and the picker chooses Cycle Scopes only. A whole-scope pair's toggle plans it into the whole flow window — the window's own kind, `1..n`, counted from the window's start like the root's. A finer Cycle Plan a pair already carries is still read and resolved, shown read-only on its row ("Day 3 · Part 2"), and the toggle clears it; no new finer plan can be made. The root Cycle Plan is one dropdown: *No plan*, **{kind} (instance scope)** — the whole flow window, kept whole if the window's length changes in the same edit — and the finer kinds, each with its cell picker. Only a task-instance root has a Plan at all: a Goal or a Commitment has none, so goal- and commitment-instance flows offer no root plan. These indices are resolved to concrete Time Scopes / Plans only when the flow is started. Existing cycle pairs list as rows; adding or editing one opens a **relative drill-down picker** modelled on the Scope Picker's own navigation (browse a level's cells, click to descend, ↑ to ascend) but labelled in relative terms ("Week 2 › Tuesday › Morning") using nominal subdivision counts (season→month 3, month→week 4, week→day 7, day→part 6) — clicking a cell at the chosen Cycle Scope Kind toggles that occurrence on or off immediately, with no separate confirm step. Part of Day cells are labelled with their real band names (Morning, Noon, …) rather than a nominal index, since that kind's meaning is fixed regardless of anchor. An Unscoped flow's items have no cycles. A **Phase**-windowed flow's items may carry finer **exact-time** cycles (a fixed `HH:MM–HH:MM` sub-range of the band/window) — permitted by design, but since these are absolute times-of-day rather than ordinal offsets they need a time-of-day cycle form and a datetime sub-interval containment check; that backend is deferred until a cycle editor supports exact times.

<a id="commitment-and-wait-items"></a>**Commitment and wait items** (Task b66; ruled by the user, 2026-10-03). Each carries every field its stored counterpart's editor has, wherever it makes sense in a template; what an occurrence's window gives it is left out.

- A **Commitment item** carries its title, privacy, tags, cycle pairs and its **Verdict Window**. Left out: its **verdict** (each occurrence is answered on its own) and its **Time Scope** (its cycle's, else the iteration's or the flow window). A Commitment takes no block reasons and has no Plan, stored or templated.
- A **wait item** carries its title, privacy, tags, cycle pairs, its **Check every** and its **first check**. The first check stands where a stored wait's *Starting* does: a template has no dates, so it is relative to each occurrence's window, in the `(kind, index)` form a Cycle Plan takes — the start of the index-th unit of that kind counted from the window's start, a part of the day counted from the part the window opens in; unset, the window's start. The Check every repeats from the first check, one interval after each check made. Left out: its **status** and **archive** (each occurrence is released or archived on its own), its **Time Scope** (its occurrence's window) and the **agent flag, note and answer** (a template wait is not one an agent raised).

Each occurrence is its own row of its kind (see [Habits](habits.md) and [Derived nodes](virtual-nodes.md)). The flow item editor shows a Commitment item's Verdict Window, and a wait item's Check every with its first check beneath it; neither offers dependencies or block reasons.

**Converting a subtree to a Flow** turns its Commitments and waits into Commitment and wait items as it turns its Tasks and Goals into theirs (ruled by the user, 2026-10-03), keeping their fields: a Commitment its Verdict Window, a wait its Check every and — when *Map scopes* is on — its Starting as a first check counted in days from the start of the window it maps to. A Task's dependency on a wait in the subtree becomes the Task item's on the wait item.

**Starting a flow** (`s` on a focused flow node, or context menu) opens a modal: title, target node (free-text search combobox; parent path shown in parentheses for duplicates; defaults to the flow's Target Node, or to its parent when it has none), and an **anchor** for the flow window. The anchor is a scope of the **flow-scope kind** (a week-flow anchors on a week, a season-flow on a season; a Duration expressed in days anchors on any day for agility), defaulting to the current such scope. On start:

- The window anchors concretely as `[anchor, anchor + (n−1) flow-kind periods]`. Each (Cycle Scope, Cycle Plan) pair resolves to a real item — **a flow item with N pairs produces N items** (an item with no pairs produces one item with no cycle scope). A Cycle Scope `(subkind K, index i)` resolves **by offset**: the K-scope beginning `i−1` K-periods after the window start (so it is always in range); the Cycle Plan resolves the same way within that cycle scope.
- The flow node materialises as a single **root** of its Instance Type, titled from the modal, with the resolved window as its Time Scope; every item becomes its descendant. An item parented on another item is placed under that parent's **first** instance.
- Intra-template dependencies **remap by fan-in**: each instance of the dependent waits on **every** instance of the blocker (Implement waits on all of this run's Specifies).
- A **Commitment item** materialises as a stored **Commitment**, over its Cycle Scope or else the flow window, carrying the item's Verdict Window; a **wait item** as a stored **wait**, over its Cycle Scope or else the flow window, keeping the item's Check every, its Starting resolved from the item's first check in that window. A Task item's dependency on a wait item becomes a stored dependency on that wait.
- A Task template's **Compound** flag and **Expectation template** (Task 611) — a flow **Task** item's, and a task-instance flow's root's — are copied onto the Task it materialises as, with its other template fields: a compound item makes a compound Task, whose status is derived from its sub-items from the moment it exists, and an Asynchronous item with a template makes a Task carrying that template as its own (`task_async_templates`), whose completion spawns its wait from it. Like every copied field they are the Task's own from then on: switching the item's Compound or editing its template afterwards changes no Task already started — the next start copies the edit — and the Task's own editor changes them on that Task alone.
- The result is a **real, independent copy** under the target. A `flow_instances` row records the run (originating flow + root), and a `flow_instance_nodes` row records each materialised node with its source flow-item and original parent — so flow-originated nodes are distinguishable from later additions and moves are detectable. The link is a "from flow X" UI indicator only (no cascading edits).
- Instances must satisfy scope containment against the Target Node. The target picker offers only scope-valid targets: at **start**, when the anchor is known, targets whose effective Time Scope window wholly contains the concrete flow window (targets with no scoped ancestor — and any Unscoped flow — are always valid); at **template edit**, before the anchor is known, a coarse necessary filter that hides only targets too small to ever hold the flow window. The backend `start` hard-rejects anything that slips through. Because a flow's materialised instances are ordinary Goals/Tasks, narrowing an ancestor's scope reconciles them through the same clamp-or-cancel prompt as any descendant (Phase 6.5); that prompt annotates flow-originated descendants with their "from flow X" origin (Phase 7.5).
