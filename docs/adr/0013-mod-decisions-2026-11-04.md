# ADR 0013: decisions for the agent-notifications mod (2026-11-04)

These decisions were made with the user in a design session on 2026-11-04. They are not yet folded into
`0013-notifying-agents-when-a-wait-resolves.md`. Whoever rewrites the ADR applies them, after first
checking the Claude Code mod API against the docs: long-lived streaming fetch, `$.prompt.submit` and
`$.session.send`, hooks on MCP tool results, a SessionStart hook or injection, persistent storage, and
reading the configured MCP servers.

**Mechanism.** A Claude Code mod (plugin) subscribes to an Arlesh server-sent event stream and wakes
the session when a wait it watches changes.

**What it no longer needs:**
- MCP tasks;
- channels;
- the `/waits/await` long-poll.

## Which waits a session watches
- Every wait the session raised. The mod sees the results of `arlesh_waits.ask` and `arlesh_waits.raise`
  through a hook.
- Any wait the agent passes to a new MCP tool, `arlesh_waits.watch(ids)`. On the server the tool only
  validates the ids and returns their current state. The mod picks up the ids through the same hook.
- A watch lasts as long as the session. Filtering the stream costs nothing.
- Watches are stored on disk per session id, so they survive a restart and `claude --resume`.
  Persisted entries are capped at about 30 days.

## Which changes wake the agent
- The wait is released or answered.
- The wait is archived or deleted. The agent is told it is gone.
- The wait is reopened, by undo or by hand.

Edits to a pending wait (its title or note) do not wake the agent.

## Event streams on the server
- `/events/changes` is today's "board changed, revision N" stream under a new name. **It replaces
  `/events` outright**: the apps switch to it in the same PR, and no alias is kept.
- `/events/expectations?agentic=true` is new. It carries typed wait events (wait id, Task id, status,
  archived or deleted) so the mod filters by id and never re-reads.
- Both the desktop app's Standalone HTTP server (beside `/mcp`) and arlesh-server serve both streams.
- **Catching up after a disconnect: read on (re)connect.** The mod keeps the last state it saw of each
  watched wait. On every connect it reads them once (`get_many`), delivers what changed, then follows
  the stream. The server keeps no history.

## Delivery
- Delivery behaves like a finished background shell command or sub-agent does today. An idle session is
  woken. A busy one gets it at the next point where the harness surfaces background events.
- **The message is a pointer only.** It is explicitly labelled as an Arlesh notification, for example
  "Arlesh notification: wait W-123 on Task 4ab changed (released); read it with `arlesh_waits.get`".
  It does not quote the answer, and it makes no difference between a resolution made through MCP and
  one made by hand.
- **Sub-agents.** The sub-agent that raised the wait gets the notification if it is still running. If it
  has finished, the session that spawned it gets it, with the sub-agent named.

## Configuration and distribution
- The mod reuses the session's configured `Arlesh` MCP server entry, its URL and headers, and opens the
  streams on the same origin with the same authentication. It has no settings of its own.
- It ships as `plugins/arlesh-notify/` with a `.claude-plugin/marketplace.json` in this repo.

## How agents learn of it and what they do
Four layers, each with its own job. Only the mod's own note says that notifications are actually on in a
session, so no agent is promised a wake-up it won't get.

- **The Arlesh MCP server instructions and tool descriptions** carry the protocol, and say nothing about
  whether the mod is present:
  - what `arlesh_waits.watch` does;
  - "if your session says Arlesh notifications are on, rely on them; otherwise don't wait on a wait".
- **AGENTS.md** carries this repo's policy (below).
- **The orchestrating-agents skill** covers the orchestrator: briefs carry the same rules to sub-agents,
  and a notification is the cue to re-read the board.
- **The mod, at SessionStart,** injects one line: "Arlesh notifications are on in this session: waits you
  ask, raise or `arlesh_waits.watch` will notify you when they change; don't poll."

### With the mod: after raising a wait the agent is blocked on
- If it has other unblocked work, it carries on. Otherwise it ends the turn and stays idle; the
  notification wakes it.
- It never polls `arlesh_waits.get` and never sleeps.
- A sub-agent reports back and finishes. The parent session gets the notification.

### With the mod: on a notification
The agent reads the wait with `arlesh_waits.get`, and its Task, then acts on the answer as the user's
input to that question, within the usual rules. Anything ambiguous means it asks again.

| The wait is | The agent |
| --- | --- |
| Released | Acts on the answer |
| Reopened | Stops any work that depended on it |
| Gone | Treats the question as withdrawn, and asks if that is unclear |

### Without the mod
- The agent still raises the hand-back wait, so the board stays truthful (AGENTS.md).
- It does not wait on that wait. It asks the question in the conversation too: to the orchestrator, or
  to the user if it is a top-level session. Then it ends the turn or reports back.
- The answer comes back through the conversation.

## Scope
- Cloud sessions are out of scope. They cannot reach a local Arlesh.
