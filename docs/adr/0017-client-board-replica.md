# Clients hold a replica of the board and run the real core on it

ADR 0012 made a press paint at once with a frontend lane of per-action patches, and it deliberately
left derived values to the server's answer. Showing derived values too needs the board's sources on
the client, and every optimistic write would need a prediction paired with it, written and kept
correct by hand. So a client now holds a **Replica**: the real `arlesh-core` over its own copy of the
board, behind a wrapper implementing the `Backend` port. A write runs on the Replica, then the same
request goes to the server. There is one implementation of the business logic, so a prediction cannot
drift from the server, and the port's traits make it impossible to add a write the wrapper misses.

## Status

accepted, built (PR 3 of Task `ccc`, 2026-11). Settled with the user. It supersedes ADR 0012. Two
answers were taken while building it: **plan triage** answers the Plan View through a pure command
keyed on the target and the board's `seq` (the scope the view is filling is window state, so it
cannot ride the board), with the parenting and take-out tables loaded once; and the Replica copies
`agent_account_usage` from `list_agents` into its own unreplicated table, since capacity blocks read
it. The press is built without a preview publication; its timing log (`arlesh::press`) is the
instrument to decide one from a real phone.

## Decisions

1. **The whole board.** In Client mode every board read comes from the Replica and every board write
   runs on it first, so every write is optimistic, with no list of which ones are.
2. **The server is the only truth.** The Replica is a disposable cache plus unconfirmed predictions.
   Fetching a snapshot repairs anything.
3. **A local refusal sends nothing.** The user sees it and retries once the board has synced. The
   server can still refuse what the Replica accepted.
4. **A gap is detected, not hoped against, and repaired with a whole board.** Each change carries its
   revision and only the next one is applied. Any gap, a reconnect, a new epoch or a content-hash
   mismatch fetches a snapshot: there is no catch-up by revision (the user, 2026-11-13: "Always a
   full board."). The server keeps no history of changes. A content hash of the board, compared
   periodically and when idle, catches a change that was never announced. It covers the replicated
   source rows (`docs/spec/client-mode.md`, *The source hash*), and `arlesh-core` computes it for
   both sides.
5. **A trigger-written Change Log feeds sync**, naming the rows each revision changed and what they
   became, and including undo and redo. The server attaches the changed rows to each live event and
   keeps no history of them. Like the Undo Journal, it cannot be forgotten by a command that does
   not know it exists. The journal itself cannot do this job: it is truncated at startup, capped, and
   written by neither undo nor redo. Built in PR 2 (migration 0111, generated by
   `scripts/generate-undo-triggers.sh change`):
   - The log is a **buffer, not a history**: the publisher empties it into each publication in the
     transaction that reads it, so nothing accumulates. The triggers write it only while a publisher
     holds a **lease** on the capture, which it renews every turn and gives up at shutdown, which
     another publisher cannot take while it is valid, and which runs out by itself after a crash.
   - The **published hash is read from the database** on every turn, not kept from the feed, so a
     change the log missed shows as a disagreement and a snapshot.
   - Rows ride only on a stream that asks (`?rows=true`): existing clients are unaffected.
   - The server-only tables are not replicated. `agents` carries stand-ins for `token_sha256`
     (`'redacted:' || id`, unique, so the row applies under the same schema) and `last_seen_at`.
   - A row is named by its `rowid`; nothing may `VACUUM`, rebuild a table or replace-insert into one
     without the triggers seeing it (`docs/spec/client-mode.md`, *Why rowid*).
6. **Hold until settled.** While writes are pending, incoming server changes are buffered. When the
   queue drains, the Replica rolls back its predictions and applies the buffered rows. A correct
   prediction changes nothing on screen, a wrong one loses to the server, and rows made by triggers
   need no handling of their own.
7. **A refused write re-runs the queue behind it** on the rolled-back Replica. What now fails locally
   is dropped, never sent, and told in one toast.
8. **A lost connection rolls back.** Pending predictions go, the app goes read-only, and catch-up
   shows the truth, including a write that did land. There is no retry and no offline queue.
9. **UUIDs are the stored identity**, as TEXT keys on every table with a surrogate integer id (31 of
   them) and on every column that names such a row. Existing rows keep their `full_id` as their id,
   so short ids and links survive (migrations 0107 to 0109). New ids are UUIDv7, which is what lets
   the same request create the same node on both sides. The id is optional on every create route
   (HTTP and MCP), so an agent or script that sends none still works and the server mints one; a
   client may send its own. Rows a write creates indirectly derive their ids from the request where
   that is practical; otherwise a press on one waits until settled. A derived id (a Habit occurrence
   and the like) is a UUID of version 8, the hash of its value key, and no stored id is ever version
   8, so the two kinds are told apart by the UUID alone.
10. **Undo is not predicted.** An unsent action is cancelled locally. Otherwise Ctrl+Z waits for the
    queue to settle and goes to the server, because after settling the Replica no longer holds a
    journal for confirmed writes.
11. **One frontend path.** Rust emits changed derived nodes as sequenced events in both modes; in
    Standalone the same pipeline runs with no server and no prediction. The pending-writes lane and
    the whole-board reload on a write go.
12. **The Replica is in-memory SQLite**, written to storage on the startup fetch and when the app
    quits normally (the user, 2026-11-13: "Memory, written on startup fetch + when quitting normally.
    Startup loads the cache first then fetches a full board."). Launch shows the cached board at once,
    read-only, and then fetches a whole board; there is no catch-up by revision. Android therefore
    ships the core and SQLite, with no local-board mode.
13. **Client and server must share a schema version.** The device snapshot carries it
    (`schema_version`, the newest applied migration). On a mismatch the app is read-only and says
    which side to update. A rule change without a schema change is tolerated: the server's answer
    corrects the prediction.
14. **No wasm.** Rust sends what the UI needs as data, so the frontend holds no rules and the build
    step goes. The `arlesh-rules` crate stays.

## Considered Options

- **Keeping the logic in the frontend through wasm.** It solves a rule disagreeing with the server,
  but every write would still need a hand-paired optimistic patch, and that pairing has nothing to
  check it. Crossing the JS and wasm boundary also cost far more than the rules themselves.
- **A pure `apply(write, sources)` per write.** It needs no database on the client, but it is a
  second implementation of every write, including what triggers and cascades do. It would need a
  conformance test to stay honest, and a Replica needs neither.
- **Client-chosen random integer ids.** This needs no migration, since row ids are plain integers,
  and it was rejected for a single identity across stored and derived rows. Reserved id blocks were
  rejected for the same reason, and because they add a route and bookkeeping.
- **Rebasing predictions on every incoming change.** Other devices' changes would show sooner, but
  each event would cost a rollback and replay. Two databases were cleaner still, at the cost of a
  full copy per rebuild.

## Consequences

- Every server migration blocks writes on a client until that client is updated. On a phone that
  means installing a new build.
- Delivery is three pull requests in order, none stacked: UUID identity, then the server's sync
  surface (Change Log, device snapshot, content hash), then the Replica and the frontend switch.
- UUID identity changes what a row number was: it is gone from the API and the MCP. The ids a caller
  holds keep working (`id` now equals `full_id`), a short id that once needed a longer prefix to
  avoid a row number may read shorter, and a Habit occurrence's id changes once, because it is the
  hash of a key that spells the ids of the rows it is drawn from.
- `/board` stays for agents and scripts, so its response time is still worth improving separately.
